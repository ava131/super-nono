## 1. 背景与目标

### 1.1 一句话描述
在 macOS 桌面上常驻一个**透明、置顶、可拖动的像素桌宠**。它是 Brain 的可视化外壳，只负责"看起来活着"和"接受你的操作"。

### 1.2 v0 目标

| 编号 | 目标 | 可衡量标准 |
|---|---|---|
| G1 | 桌宠常驻桌面 | 透明无边框、始终置顶、不占 Dock |
| G2 | 能停靠 | 固定停在屏幕某处，重启后回到原位（按屏幕比例还原） |
| G3 | 能拖动 | 按住可拖到任意位置，松手停住，不越界 |
| G4 | 有生命感 | 待机动画持续播放，思考/说话有不同表现 |
| G5 | 能对话 | 单击宠物弹出**独立对话框窗口**，流式显示 Brain 的回复 |
| G6 | 资源可控 | 常驻内存 ≤ **500MB**，空闲 CPU ≤ 3% |
| G7 | 美术可替换 | v0 用程序化占位像素图，之后换图不改代码 |

> **关于产品侧成功指标**：本次评审提出「v0 缺少产品指标」，**PM 决定暂不写入**。v0 以本文档 §8 的工程验收为准。

### 1.3 v0 非目标（明确不做）

- ❌ **Ctrl+M 飞行 / 点击桌面飞过去**——移交 v1+
- ❌ **多显示器**——PM 明确：v0 完全不碰，**不再讨论、不再测试**（唯一例外是 §W-1 的比例坐标，见下）
- ❌ 跨平台（Windows / Linux）——移交 v1+
- ❌ **宠物缩放（1x / 2x）**——PM 决定 v0 不做，设置面板不含此项
- ❌ 语音输入 / 语音播报
- ❌ 自动操作其他 App（点击别人窗口、自动填表）
- ❌ 粒子特效、Live2D、骨骼动画、换装
- ❌ 「对话内容会发送到 DeepSeek」的面向用户提示——PM 决定不做（自用 toy）

## 4. 功能需求

### W-1 透明置顶悬浮窗【P0】

- 无边框、背景全透明、无窗口阴影、不可缩放。
- 置顶层级需盖住普通窗口，切换桌面空间（Space）时跟随显示。
- **不占 Dock**（accessory 模式，`app.dock.hide()`），只在菜单栏托盘有一个图标。
- 窗口尺寸 = 精灵尺寸 + 四周留白（**留白不参与命中测试**）。v0 定死为 **160×160**，精灵 **96×96**，四周各留 32px 用于动画溢出。
- ⚠️ **气泡不是这个窗口的一部分**：对话框是**独立的 `bubbleWindow`**（见 W-5）。因此宠物窗尺寸**永远不受气泡影响**，`160×160` 是一个常量。
- **位置持久化**：保存为**当前 `workArea` 的比例坐标** `{ rx, ry }`（如 `{ "rx": 0.87, "ry": 0.92 }`），启动时按当前屏幕乘回去。
  - 收益：换电脑或改分辨率后**永远不可能越界**，连"坐标是否在屏内"的判断都不用写。
  - 首次启动（无存储值）落在主显示器 `workArea` 右下角。

### W-2 点击穿透与命中测试【P0】

- 鼠标在宠物**透明区域**时：事件穿透到下层，不阻挡用户操作。
- 鼠标在宠物**实体像素**上时：正常接收事件（悬停、按下、点击、拖动）。
- 判定依据：当前帧的 **alpha 通道**，`alpha > 10` 视为实体像素。
- ⚠️ 必须做**状态防抖**：鼠标停在像素边缘时不能反复切换穿透开关。做法是 alpha 滞回：**进入阈值 `ENTER = 30`（alpha 必须高于它才认定压在像素上）、退出阈值 `EXIT = 10`（alpha 必须低于它才恢复穿透）**，中间的 10–30 是滞回带，保持原状态不变。
  - ⚠️ **这两个数的大小关系不能反。** v0.1 原稿误写为"进入 10 / 退出 30"——那样 alpha 落在 10–30 之间时状态会**每个事件翻转一次**，反而变成振荡器。**进入必须用高阈值、退出必须用低阈值。**（该错误由 `test/unit/hit-test.test.js` 的"反复喂同一个中间值不会导致状态振荡"用例抓出）
- **方案 B 的关键收益**：因为气泡是独立窗口，穿透逻辑**只需考虑宠物窗**，判定就是纯粹的 alpha 测试——不需要「alpha ∪ 气泡矩形」两套逻辑，这是最容易出玄学 bug 的地方。
- 频道：渲染进程通过 `pet:setIgnoreMouse` 通知主进程切换（见 W-9）。

### W-3 拖动【P0】

- 按住宠物实体像素 → 跟随鼠标 → 松手停住。
- **不使用系统窗口拖动方案**，自行实现，理由：拖动过程中要播放动画、要限制范围。
- **实现要点**：窗口很小，快速拖动时鼠标会跑出窗口外导致丢事件。因此**拖动期间由主进程轮询 `screen.getCursorScreenPoint()` 并调用 `win.setPosition()`**，不依赖渲染进程的 `mousemove`。
- 边界约束：宠物中心不得离开当前 `workArea`。
- 拖动时播放 `drag` 状态动画。
- 拖动结束后持久化位置比例（见 W-1）。

#### W-3.1 点击 vs 拖动的判定阈值【P0 · 硬性数字】

评审指出：若 `mousedown` 后立即进入拖动，用户手抖 2 像素就会被判成拖动，**气泡弹不出来**。因此必须定死阈值：

| 条件 | 判定 |
|---|---|
| `mousedown` 后**未**满足下行任一条件就 `mouseup` | **点击** → 发 `pet:click`（切换气泡窗显隐） |
| 累计位移 > **4px** **或** 按住 > **250ms** | **拖动** → 才启动 16ms 轮询 |

- 数字可调，但**必须是一个数字**，否则 A3/A4/A6 的测试用例没法写。
- 阈值常量集中在 `src/renderer/pet.js` 顶部，便于调参。

### W-4 动画状态机【P0】

| 状态 | 触发 | 动画要求 | v0 |
|---|---|---|---|
| `idle` | 默认 | 循环，4–8 帧，有呼吸/眨眼 | ✅ |
| `drag` | 拖动中 | 循环，2–4 帧 | ✅ |
| `think` | 已发出请求、等首个 token | 循环 | ✅ |
| `speak` | 流式输出中 | 循环 | ✅ |
| `error` | 出错 | 单次播放后回 idle | ✅ |
| `happy` / `sleep` / `fly` | — | — | ❌ v1+ |

- 帧率固定 **10 fps**（不要 60fps：省 CPU，且像素风更有味道）。
- 状态切换可打断、可排队，避免卡死。
- **状态来源与优先级**（评审发现的歧义，此处定死）：
  - `brain:state`（主进程下发）与本地交互状态（`drag`）可能同时存在。
  - **优先级：本地交互态 > 主进程下发态**。即拖动期间无论主进程说什么，都显示 `drag`；松手后回落到最近一次 `brain:state`。
  - 调试面板显示的是"合并后的最终状态"，并在括号里标出来源，避免来回跳。

### W-5 对话框（气泡窗 `bubbleWindow`）【P0】

**v0.1 架构变更：气泡是独立的新窗口，不是宠物窗的一部分。**（评审决定 1）

- **单击宠物** → `bubbleWindow.show()`；再次单击 / Esc / 点别处 → `hide()`。
- **窗口属性**：
  - `focusable: true`（宠物窗为 `focusable: false`）——键盘输入必须落在气泡窗上。
  - 普通窗口外观（不透明、有圆角），**没有透明区域，因此不需要任何穿透处理**。
  - 尺寸约 380×420（待实测微调），可容纳消息列表、输入框、停止按钮、确认弹窗、设置面板。
- **生命周期**：**只创建一次**，打开 = `show()`，关闭 = `hide()`，**绝不 `destroy()`**（沿用 §6.3 防泄漏第 1 条）。
- **定位规则（由主进程计算，渲染进程不掺和）**：

  ```
  x = petCenterX - bubbleW / 2
  y = pet.y - bubbleH - 8
  ```

  - 贴边则 `clamp` 到当前 `workArea` 内。
  - 上方空间不足则**翻转到宠物下方**。
- **宠物拖动时**：直接**隐藏气泡窗**（松手后不自动弹回）。比"跟随移动"实现简单，且避免高频 `setBounds`。
- **关闭行为**：Esc / 点击气泡外由气泡窗自己监听，**不需要跨窗口协作**。
- **内容与交互**：
  - 消息列表 + 输入框 + 发送
  - 回复**流式**逐字显示，显示期间宠物状态为 `speak`
  - 必须有「**停止**」按钮中断正在生成的回复（硬需求）
  - 必须能显示 L2 操作的确认弹窗（见 `PRD-Skill-v0.md` §4.2）
  - 内嵌设置面板（见 W-7）
  - Markdown 只需支持：段落、列表、粗体、行内代码、代码块
- **流式渲染优化**：`brain:delta` 不直接触发 DOM 更新，先进队列，按 **16–60ms 批量 flush**（合帧渲染），避免长回答时每帧多次 reflow。

#### W-5.1 操作反馈【P0 · v0.4 新增】

**每一个写操作都必须有可见的反馈。**（这条来自实施期的一个真 bug：设置保存成功，但提示被追加进了当时处于隐藏状态的聊天视图，用户以为没保存。）

| 操作 | 反馈方式 |
|---|---|
| 保存设置 | 面板级 **toast**（浮层，不依赖当前视图），2.6 秒后自动消失 |
| 清空当前对话 | toast + 聊天区重置为问候语 |
| 新建 / 切换对话 | toast + 聊天区重新渲染 |
| 出错 | 聊天区一条 `⚠️` 系统消息 |

- **toast 必须挂在面板层**（`position:absolute`），不能在某个视图内部——否则切走视图就看不见了。
- toast 分三态：成功（绿）/ 警告（黄）/ 错误（红）。

#### W-5.2 打开时渲染历史【P0 · v0.4 新增】

- 气泡窗打开时必须读取当前会话的最近消息并渲染。
- 否则会出现"消息确实存了、Agent 也确实记得，但用户看到的是一片空白"的割裂状态。
- 无线程时显示问候语。

#### W-5.3 状态文案不得硬编码"当前能力"【P0 · v0.6 新增】

**开场提示必须从真实状态推导，不能写死。**

这条来自一个真 bug：M2 阶段（还没有技能）在 `ipc.js` 里写了一句

```js
settings.hasApiKey() ? '（还没接技能，我暂时只能聊天。）' : '还没填 API Key…'
```

M3 把天气技能接上之后，前半句变成了**假话**——用户一打开气泡就被告知"只能聊天"，紧接着又问出了真实天气。用户实测发现。

规则：

| 要求 | 说明 |
|---|---|
| 不写死能力 | 「有/没有技能」「能/不能查天气」这类会随版本变化的信息，**要么从注册表推导，要么不说** |
| 有 Key 就不打扰 | 配了 API Key 就能聊；技能有几个都不影响"能不能用"，所以**不该有开场提示** |
| 只提示可修的 | 唯一值得主动说的是"有技能因清单写错被禁用"——那是用户能修的 |
| 一次就够 | 每次打开气泡都念一遍同一句话是噪声；**每次运行最多提示一次** |
| 优先说最紧急的 | 没 Key 时只说 Key，不让技能错误抢戏 |

实现落在 `src/main/brain/status.js` 的 `openHint()`（纯函数），并由 `test/unit/status.test.js` 锁定——其中一条用例专门检查提示语里**不得出现任何能力断言**（`暂时只能` / `还没接` / `没有技能` / `不能查`）。

### W-6 托盘与生命周期【P0】

- 菜单栏托盘图标，菜单：显示/隐藏宠物、设置、打开数据目录、退出。
- 无主窗口概念，关闭窗口 ≠ 退出应用。
- 开机自启开关（默认关）。
- 单实例锁：重复启动只唤起已有实例。

### W-7 设置面板【P0，极简版】

v0 只保留必要项：

- DeepSeek API Key
- 模型选择（默认 `deepseek-chat`）
- 开机自启
- **一键清理本地数据**（语义见下）
- 数据目录位置

> **v0 不含**：宠物缩放（已砍）、快捷键设置（飞行功能已砍）、外观设置。

#### W-7.1 API Key 的存储方式【P0 · 统一口径】

评审指出 Body 与 SDD 的表述冲突，**此处统一为 SDD 方案**：

- 使用 Electron 内置 `safeStorage.encryptString()` 加密后，将**密文**写入 `config.json`；明文只存在于内存。
- **降级分支（必须实现）**：当 `safeStorage.isEncryptionAvailable() === false` 时，**禁止明文回退**——必须明确报错并告知用户"当前系统无法安全存储密钥"，由用户决定是否继续（不静默降级）。
- 密钥的读取只发生在主进程 `settings.js` 一处。

#### W-7.2 首次启动无 API Key 的处理【P0】

- 应用启动后若检测到 **API Key 缺失**，宠物直接在气泡里给一句提示，引导去设置面板填入 Key。
- **不做**复杂新手引导、不做分步 wizard、不做欢迎页。
- **不做**"没有 Key 就不能启动"这类硬拦截——宠物仍然活着（`idle` 动画照常），只是不能对话。
- 提示文案由开发拟定（简短、符合 NONO 人格：先给结论、不啰嗦），**不设产品评审关卡**。
- 与 `PRD-Brain-v0.md` B-8 的"API Key 无效/缺失 → 提示去设置"是**同一条链路的两个触发时机**（启动时 vs 请求时），实现上**复用同一套提示逻辑**。

#### W-7.3 破坏性操作的**作用域归属**【P0 · v0.5 重写】

> **原稿写的是"应用级一键清理本地数据"，那是在只有单会话时定的。有了多会话之后，这个入口放错了地方——见下方「作用域原则」。**

##### 作用域原则（v0.5 确立）

**每个操作必须放在它所作用的对象的层级上。** 本应用只有两个作用域：

| 作用域 | 含义 | 该放的操作 | 界面位置 |
|---|---|---|---|
| **应用级** | 全局，只有一份 | API Key、模型、每日费用上限、飞行模式、数据目录 | 齿轮 ⚙ |
| **会话级** | 针对某一个对话 | 新建、切换、**重命名**、**删除** | 对话列表 ☰ |

- ❌ 反面教材（v0.4 犯的错）：把「清空当前对话」放进了齿轮。它是会话级操作，放进应用级设置里，齿轮就变成了杂物抽屉。
- ❌ 另一个反面教材：会话列表里**一个操作都没有**——能新建却不能删除，列表只增不减。
- 这两件事是同一个病根：**把"会话"当成一个有完整生命周期的对象了吗？没有。** 数据层（`sessions` 表的 `id/title/created_at/updated_at`）早就为完整生命周期准备好了，但只实现了 `create/switch/list`，缺 `delete`，而唯一那个破坏性操作还被挂错了层级。

##### 会话级操作（在对话列表里就地完成）

| 操作 | 交互 | 说明 |
|---|---|---|
| **删除** | 点 🗑 → **该行就地展开确认条** → 「算了」/「删掉吧」 | 报出**是哪个对话**（「对话名」），不遮挡列表 |
| **重命名** | 点 ✎ → 标题变输入框 → Enter 或失焦保存，Esc 取消 | 手动改过的名字，后续自动起标题不会覆盖 |

**删除的确认语气照 Minecraft 删除世界的确认框**（PM 提供原话：*确定要删除这个世界吗？'（世界名）'将会永久失去！（真的很久！）*）：

> 确定要删除这个对话吗？
> **「帮我写一个500字关于赛尔号的作文」**
> 将会永久失去！（真的很久！）

- **「真的很久！」这种调子要保留**——这是这只宠物的性格，也让删除这种重操作带点人味。
- 原稿担心"「（世界名）」那个位置填不出东西"——**多会话 + 自动标题之后，这个位置终于名副其实了**。

##### 删除的边界行为（硬性）

| 情况 | 行为 |
|---|---|
| 删的不是当前会话 | 当前会话不变 |
| 删的是当前会话，还有别的 | **自动切到最近的一个**，并提示 |
| 删到最后一个 | **自动新建一个空会话**，绝不允许出现"零会话"状态 |
| 删一个不存在的会话 | 返回失败，**不破坏任何状态** |

##### 其他

- 删除**不可逆**，**不允许一键直接清掉**，必须先确认。
- 用量统计与日志**保留**；API Key、宠物位置与外观**不受影响**。
- v0.5 起**应用级不再有"清空全部聊天记录"入口**。如果将来觉得需要（比如攒了几十个对话想一键清空），它确实是应用级操作，放齿轮里是正确的——届时再加。

### W-8 调试面板【P0，开发者自用】

- 快捷键 `Ctrl+Shift+D` 唤起，显示：
  - 当前状态名（含来源标注，见 W-4）
  - FPS
  - **主进程 + 全部子进程的内存占用，并带最近 5 分钟的曲线**（慢速泄漏看瞬时值看不出来，看曲线一眼就知道——这是 24h 跑测的核心关切）
  - 最近日志
  - 最近一次请求的 token / 费用 / 延迟（数据来自 Brain）
- **内存数据由主进程定时推送**（`debug:metrics`），因为渲染进程读不到主进程的内存。
- **这是"资源占用不失控"的观测手段**，属于 v0 必要投入。

### W-9 与 Brain 的 IPC 契约【P0 · **v0 草案，M2 开始时冻结**】

> **状态变更（评审决定 4）**：原稿把本契约标为「冻结」，但它缺少 4 类必要频道，按它**写不出可运行的代码**。
> **冻结一个跑不起来的契约，比不冻结更贵**——大家会以为它是对的，照着写，然后在 M2 撞墙。
> 因此：**M0/M1 期间允许自由增补频道，M2 开始时才正式冻结。** 冻结时至少补齐下列全部频道。

**渲染进程 → 主进程**

| 频道 | 载荷 | 用途 | 状态 |
|---|---|---|---|
| `pet:ready` | 无 | 界面就绪，请求初始状态 | 原 |
| `pet:userMessage` | `{ text }` | 用户发送消息 | 原 |
| `pet:cancel` | 无 | 中断当前生成 | 原 |
| `pet:toggleBubble` | `{ open: boolean }` | **显式设置**气泡窗状态。由气泡窗自身（Esc / 关闭按钮）与托盘菜单发出 | 原 |
| `pet:dragStart` | `{ offsetX, offsetY }` | 开始拖动（**仅在超过阈值后触发**） | 原 |
| `pet:dragEnd` | 无 | 结束拖动，主进程持久化位置比例 | 原 |
| `pet:stateChanged` | `{ state }` | 渲染进程**本地**状态上报（主要是 `drag`） | 原，语义已澄清 |
| `pet:confirmResponse` | `{ requestId, approved }` | 用户对 L2 操作的确认结果 | 原 |
| **`pet:click`** | 无 | **点击判定成立**（未升级为拖动）。渲染进程只负责"报告这是一次点击"，**由主进程决定 toggle 气泡窗**——避免渲染进程自己维护显隐状态导致两边不一致 | **新增** |
| **`pet:setIgnoreMouse`** | `{ ignore: boolean }` | **切换点击穿透**（原 SDD 示例代码用了它却没定义） | **新增** |
| **`settings:get`** | `{ keys }` | **读取设置（invoke）** | **新增** |
| **`settings:set`** | `{ key, value }` | **写入设置（含 API Key，invoke）** | **新增** |
| **`settings:clearData`** | `{ scope: "messages" }` | **清空当前对话（invoke，需先经确认弹窗）** | **新增** |
| **`history:recent`** | `{ limit }` | **读取当前会话最近 N 条（invoke）** | **v0.4 新增** |
| **`session:list`** | 无 | **列出全部会话（invoke）** | **v0.4 新增** |
| **`session:new`** | 无 | **新建会话并切过去（invoke）** | **v0.4 新增** |
| **`session:switch`** | `{ id }` | **切换会话（invoke）** | **v0.4 新增** |

**主进程 → 渲染进程**

| 频道 | 载荷 | 用途 | 状态 |
|---|---|---|---|
| `brain:state` | `{ turnId, state }` | 让宠物体现在做什么 | **加 `turnId`** |
| `brain:delta` | `{ turnId, text }` | 流式增量文本 | **加 `turnId`** |
| `brain:message` | `{ turnId, role, text, done }` | 一条完整消息 | **加 `turnId`** |
| `brain:notice` | `{ turnId, level, text }` | 系统提示（非对话类） | **加 `turnId`** |
| `brain:error` | `{ turnId, code, message }` | 错误，界面转 `error` 状态 | **加 `turnId`** |
| `brain:confirmRequest` | `{ requestId, skill, args, preview }` | 请求用户确认 L2 操作 | 原 |
| **`debug:metrics`** | `{ mainRss, rendererRss[], gpuRss, samples[] }` | **主进程定时推送内存指标** | **新增** |

**为什么必须加 `turnId`（评审 §3.3 ④）**：用户点「停止」后立刻又发一条新消息时，旧请求的 `brain:delta` 可能还在路上飞。没有标识就会**串台**——上一轮的字飘进新气泡。这是偶发、难复现的一类 bug。**所有 `brain:*` 事件必须带 `turnId`，渲染进程丢弃不属于当前轮的事件。**

**`pet:stateChanged` 与 `brain:state` 的合并规则**：见 W-4 末尾（本地交互态优先）。

**通用约定**：
- 频道名统一 `域:动作` 格式；载荷必须可结构化克隆；不传 Buffer、不传函数。
- 频道常量集中在 `src/shared/channels.js`，两端共用同一份，**禁止手写字符串**。
- 渲染进程发来的所有入参，**主进程必须再校验一次**（渲染进程不可信）。

## 5. 美术资源规范

### 5.1 v0 策略：程序化占位图

v0 **不画任何图**。用代码在离屏 canvas 上绘制一个 **96×96** 的像素形象（v0 可以是简单的方块/圆脸），生成 2–4 帧"呼吸"动画。

- 目的：先把整条链路跑通（窗口 → 动画 → 拖动 → 命中测试 → 对话），美术随时可换。
- 附加收益：这一层抽象顺便验证了 G7「换图不改代码」。

### 5.2 资源规范（为 v1 换真图预先冻结）

| 项 | 规定 |
|---|---|
| 图集格式 | PNG（Sprite Sheet）+ JSON（帧坐标描述，Aseprite 可直接导出） |
| 命名 | `assets/sprites/<状态名>.png` / `.json`，如 `idle.png`、`think.png` |
| **逻辑尺寸** | **96×96**（与 §W-1 的窗口尺寸对齐：96 精灵 + 每边 32 留白 = 160 窗） |
| 导出倍率 | **@2x（192×192）**，供 Retina 屏保持锐利；渲染时按 CSS 尺寸绘制 |
| 锚点 | 统一「脚底中心」，便于拖拽与贴地 |
| 色板 | 全局统一一套 16–24 色像素色板，避免风格漂移 |
| 透明 | 背景必须全透明，**不得有半透明描边**（会污染命中测试） |
| 帧数上限 | 单状态 ≤ 12 帧 |
| 加载 | 启动时一次性加载全部图集（总量控制在几 MB 内） |

> **关于缩放**：v0 **不做** 1x/2x 缩放功能。若 v1+ 恢复该功能，实现方式是**窗口 bounds 的整数倍缩放**（像素画整数倍放大不会糊），因此**图集永远只需要一套**，不需要按倍率再画一套图。

### 5.3 v0 必备动画

`idle`、`drag`、`think`、`speak`、`error`。全部由占位图生成。

## 6. 性能预算（重点）

### 6.1 内存

**v0.1 重算**：因气泡采用**独立窗口（方案 B）**，渲染进程从 1 个变为 **2 个**。

| 进程 | 数量 | 典型占用 | 说明 |
|---|---|---|---|
| Main（主进程，含 Brain） | 1 | 60–100 MB | Node 运行时 + SQLite |
| **Renderer（宠物窗 + 气泡窗）** | **2** | **160–300 MB** | Chromium 渲染引擎，**与窗口数量成正比** |
| GPU Helper | 1 | 40–80 MB | 合成与光栅化 |
| Utility / Network | 1 | 20–40 MB | 网络与杂项 |
| **合计常驻 RSS** | | **约 280–520 MB** | |

> ⚠️ **A9 上限因此从 300MB 放宽到 500MB。这是「气泡独立窗口」架构的已知代价，用户已明确接受（16GB M2 上为一个 160×160 宠物多花约 100MB 被认为划算）。**
>
> 这条代价必须在此**明确认账**，不能装作没发生——否则 M4 一测就"不达标"，然后回头吵架。
> 换来的是：**命中测试保持纯净**（宠物窗永远是 160×160，穿透判定就是一行 alpha 测试），避开了方案 A 中最容易出玄学 bug 的地方。

- **显存几乎不占**：像素图集只有几 MB 纹理，硬件合成开销可忽略。
- **磁盘**：v0 不打包，开发态直接跑；打包后 `.app` 约 150–250MB（内含 Chromium）。

### 6.2 CPU

| 场景 | 目标 |
|---|---|
| 空闲（仅 idle 动画） | ≤ 3%，期望 1% 级 |
| 拖动中 | ≤ 10% |
| 流式输出中 | ≤ 15%（主要是网络等待；合帧渲染进一步降低 DOM 开销） |
| 宠物窗与气泡窗都隐藏时 | ≈ 0% |

关键手段：**10fps 而非 60fps；窗口不可见时暂停渲染循环。**

### 6.3 防内存泄漏清单（v0 验收项，逐条执行）

1. **窗口只创建一次**：宠物窗与气泡窗都常驻，隐藏/显示而非销毁/重建。
2. **动画循环受状态驱动**：不做永久 `requestAnimationFrame` 空转；隐藏时停掉。
3. **定时器集中管理**：状态切换时清理上一状态定时器，禁止散落的 `setInterval`。**拖动轮询定时器必须在 `dragEnd` 清理。**
4. **IPC 监听器成对释放**：禁止重复 `addListener` 而不移除。
5. **流式请求必须可 abort**：取消、超时、出错三条路径都要销毁底层连接。
6. **消息历史有上限**：内存中只保留最近 N 条（建议 40），更早的落 SQLite。
7. **日志用环形缓冲**：内存中最多 500 条，超出写文件。
8. **SQLite 单连接 + WAL 模式**。
9. **少 resize**：透明窗口频繁改尺寸在部分 Electron 版本上有内存增长问题。**拖动时不要改宠物窗尺寸；气泡窗定位用 `setBounds` 而不是反复 `setSize`。**
10. **可观测**：调试面板常驻显示内存**曲线**（见 W-8）。

### 6.4 与替代方案对比（记录决策依据）

| | Electron（v0 采用） | Tauri v2（v1+ 备选） |
|---|---|---|
| 安装包 | 150–250 MB | 5–15 MB |
| 常驻内存 | 约 280–520 MB（双窗口） | 60–120 MB |
| 空闲 CPU | 1–3% | < 1% |
| 开发速度 | 快，透明窗口坑少 | 慢，WebView 透明有坑 |

> 架构上强制 Body 保持「薄」（只做窗口/动画/交互/IPC），是为了将来真要换 Tauri 时只需重写这一层薄壳。

| A11 | CPU | 空闲状态 CPU ≤ 3% |

| A14 | 清理确认 | 点「清理数据」必先弹确认框，框内列出将删除的内容；确认后只清空消息历史，**用量统计与日志保留，API Key 不受影响** |

#### A9 / A10 的测量方法（写死，避免"开发说过了、测试说没过"）

```bash
# 1. 冷启动应用，静置 5 分钟，不做任何交互
# 2. 取 Main 进程 PID（开发态）
MAIN=$(pgrep -f "Electron .*super-nono" | head -1)
# 3. 求和：命令行中包含本项目标识的全部进程 RSS
ps -Ao rss,command | grep -i "super-nono" | grep -v grep \
  | awk '{s+=$1} END {printf "A9 RSS = %.0f MB\n", s/1024}'
```

- **口径**：主进程 + 全部子进程（Renderer / GPU / Utility）的 RSS **之和**，**不是**只看主进程。
- 打包后进程名变为应用名，把关键字换成 `Super Nono` 即可。
- 交叉核对：用活动监视器搜索同一关键字，确认没有混入其他 Electron 应用（如 VS Code）。
- A10 的 24h 跑测**必须脚本化**，见 `SDD-v0.md` §9 的 `pnpm soak`。

## 10. 风险

| 风险 | 影响 | 应对 | 状态 |
