## 1. 背景与目标

### 1.1 一句话描述
Brain 是一个**极简 Agent 框架**：接收用户在气泡里说的话，调用 DeepSeek 模型，按需调用技能（Skill）拿真实数据，把结果流式吐回给 Body。

### 1.2 v0 目标

| 编号 | 目标 | 可衡量标准 |
|---|---|---|
| G1 | 能对话 | 输入中文提问，流式返回，可中断 |
| G2 | 有人格 | 以 NONO 的设定回应，简短、有性格、不啰嗦 |
| G3 | 会调技能 | 模型能自动决定调用技能（v0 用天气技能验证），并消费结果 |
| G4 | 记得住 | 重启应用后仍记得历史对话 |
| G5 | 密钥安全 | **API Key 绝不出本机**：进钥匙串、不入日志、不界面明文 |
| G6 | 成本可见 | 每次请求记录 token 用量与费用估算 |

### 1.3 v0 非目标（移交 v1+）

- ❌ 定时任务与主动性（"每天早上看一眼…"）
- ❌ 长期记忆（它主动记住你的偏好）
- ❌ 多智能体 / 子 Agent 编排
- ❌ 大型 RAG 知识库、向量检索
- ❌ 微调、本地模型
- ❌ 语音识别与合成
- ❌ 供应商多路切换的 UI（适配层留好接口，v0 只用 DeepSeek）

## 2. 已确认的隐私与安全边界

### 2.1 结论（已拍板）

> **红线是「API Key 不能外流」；对话内容发给 DeepSeek 云是预期行为，已接受。**

据此固化为以下可执行条款：

| 编号 | 条款 | v0 |
|---|---|---|
| P-1 | 本应用**唯一的对外通道是 DeepSeek API**，不接第三方 SDK、不埋点、无遥测 | ✅ |
| P-2 | **API Key 是本项目最高密级的秘密**：存 macOS 钥匙串，不写明文配置，不进日志，界面掩码，出错信息中不得回显 | ✅ |
| P-3 | 除 DeepSeek 外的一切网络请求，必须在技能的网络白名单里显式声明（见 `PRD-Skill-v0.md` §4） | ✅ |
| P-4 | 所有数据落盘在本地，路径 `~/Library/Application Support/super-nono/` | ✅ |
| P-5 | 日志脱敏：默认不记录完整消息体，调试模式下记录时给出明确警告 | ✅ |
| P-6 | 提供「飞行模式」开关：一键彻底断网（桌宠仍在，但无法对话） | ✅ |

- v0 技能只有天气查询，其数据源选为**无需 API Key 的公开接口**（见 `PRD-Skill-v0.md` §6），因此 v0 的密钥管理面只有 DeepSeek 一个。

### 2.2 模型选择

| 模型 | 用途 | 注意事项 |
|---|---|---|
| `deepseek-chat` | **v0 默认**，对话 + 工具调用 | 工具调用支持稳定，延迟低 |
| `deepseek-reasoner` | 复杂分析（v1+） | 慢、贵；**其工具调用支持需实现时实测确认**，不支持则不得用于需要技能的场景 |

- 接口为 OpenAI 兼容格式（`baseURL` 指向 DeepSeek）。适配层写一次，将来换供应商成本极低。

## 3. 架构位置

```
Electron 应用（单进程树）
├── Main 进程   ← Brain 在这里（Node 环境：可读文件、可连网络、可开数据库）
│   ├── 模型适配层（DeepSeek / OpenAI 兼容）
│   ├── 会话循环 + 工具调用循环
│   ├── 记忆（SQLite）
│   ├── 成本统计
│   └── 技能注册表 → 调用 Skill
└── Renderer 进程 ← Body 的宠物界面（只负责显示与输入）
```

### 3.1 Brain 需不需要做前后端？

**不需要。这是明确结论。**

- 传统意义的「后端」= Brain：它跑在 Electron 主进程里，本身就是一个具备文件、网络、数据库能力的 Node 进程。
- 传统意义的「前端」= Body：宠物窗口 + 气泡 + 设置面板。
- 两者之间不是 HTTP，而是 **Electron IPC（进程内消息）**：**没有端口、没有本地服务器、没有多余进程**。
- 项目形态：**一个应用、两个进程、零后端服务。**

**唯一例外**：将来若为使用某个 Python 库而把 Brain 换成 Python，才需要拆独立进程走本地通信。**当前不做**，理由见 §9。

## 4. 功能需求

### B-1 模型适配层【P0】

- 统一接口 `chat({ messages, tools, stream })`，返回异步流。
- 必须支持：流式输出、工具调用（function calling）、超时、取消。
- `baseURL` / `apiKey` / `model` 抽成配置；DeepSeek 只是其中一组默认值。
- 不把 DeepSeek 特有字段泄漏到上层业务代码。

### B-2 会话循环【P0】

一次"提问 → 回答"的完整流程：

1. 组装上下文：系统人格 → 最近 N 条对话 → 用户新消息。
2. 带技能清单发起请求（流式）。
3. 若模型返回工具调用：检查权限 → 执行技能 → 把结果作为工具消息回填 → **再次请求模型**（循环）。
4. 直到模型给出最终文本，流式转发给 Body。
5. 落盘本轮记录（消息、token、耗时、调用了哪些技能）。

**硬性约束**

| 编号 | 约束 |
|---|---|
| B-2a | 工具调用循环**最大步数 5**，超出则中止并告知用户 |
| B-2b | 单次请求超时 60s；单次技能执行超时按技能声明（默认 15s） |
| B-2c | 全程可取消：用户点「停止」→ 立刻 abort 网络连接并终止循环 |
| B-2d | 技能失败不崩溃，错误作为工具结果回填，让模型自行解释 |
| B-2e | 同一技能连续失败 2 次后禁止再调，避免死循环烧 token |

### B-3 人格（Persona）【P0】

- 人设：赛尔号里的 NONO——随身的 AI 助手，不是客服，不是工具人。
- 语气要求：
  - 中文回答，**先给结论，再给理由**
  - 简短，能一句说清就不写三段
  - 有一点自己的性格（好奇、偶尔吐槽），但不油腻、不刷颜文字
  - 不谄媚，不说"作为一个AI语言模型"
- 系统提示词必须包含：身份、语气规范、可用技能及其使用时机、安全规则（不得编造实时数据）。
- **⚠️ 系统提示词中不得包含当前时间**（v0.1 修订，见下方 B-3.1）。
- 人格提示词存为**可编辑的文本文件**，方便随时调，不用改代码。

#### B-3.1 当前时间的注入位置【v0.1 修订 · 重要】

**原稿的错误**：旧版要求"系统提示词必须包含当前时间"，但这与 B-6e「保持系统提示词前缀稳定以提高上下文缓存命中率」**直接互斥**——时间精确到分钟，前缀每分钟一变，缓存命中率≈0，B-6e 这条写在成本控制章节的优化等于白写。

**修订后的做法**：时间**不进 system message**，而是拼在**本轮 user 消息前面**：

```
[现在是 2026-09-11 14:20 周四] <用户原话>
```

- system message 中只剩人格 + 技能清单 + 安全规则，**一个字都不随请求变化**。
- **为什么不改成"调一次天气技能拿时间"**（曾考虑过，已否决）：
  1. 它只解决"天气"这一个场景。B-3 要时间是为了「今天几号」「还有几天到周末」这类问题，**跟天气无关**；天气技能返回的是**观测时间**，不是系统时间。
  2. 多一次工具调用 = 多一次模型往返 = **更慢更贵**，而时间是已知信息。
  3. 时间语义不同：天气的观测时间戳（`PRD-Skill-v0.md` §6.4 WX-3）表达"数据是哪一刻观测的"，与"现在是几点"是两件事，不该合并。

**收益**：B-3 的时间感知照样满足（AB4 照样过）；B-6e 的稳定前缀真正成立；不新增任何工具调用。

### B-4 记忆【P0 基础】

| 层次 | 内容 | 实现 | v0 |
|---|---|---|---|
| 短期 | 最近 N 条对话 | 内存数组（上限 40 条）+ 落 SQLite | ✅ |
| 会话持久化 | 重启后能继续上文 | SQLite | ✅ |
| **多会话** | **新建 / 历史列表 / 切换**（v0.4 由 PM 决定纳入 v0；启动开新会话，最近会话为空则复用） | SQLite `sessions` 表 | ✅ |
| 会话摘要压缩 | 超出窗口的对话压缩 | 定期调用模型生成 | ❌ v1+ |
| 长期事实记忆 | 记住你的偏好与背景 | SQLite + 可查看可删除 | ❌ v1+ |

- v0 明确不做：把整份聊天记录无脑塞进上下文（又贵又慢还降智）。

### B-5 数据与隐私【P0】

- 数据落地位置：`~/Library/Application Support/super-nono/`
  - `nono.db`（SQLite：消息、用量）
  - `logs/`（按天滚动 JSONL）
  - `config.json`（非敏感配置）
- API Key：用 Electron 内置 `safeStorage`（底层就是 macOS 钥匙串）加密后存储。
- 日志脱敏：默认不记录完整消息体；调试模式记录时给出明确警告。
- 出网管控：所有网络请求统一走 `safeFetch`，域名不在白名单直接抛错（见 `PRD-Skill-v0.md` §4）。
- 飞行模式：设置项一键切断所有出网请求。

### B-6 成本与预算控制【P0】

| 编号 | 要求 |
|---|---|
| B-6a | 每次请求记录：模型、输入 token、输出 token、缓存命中 token、耗时、**费用估算**。记账**只写 `usage_log` 一处**，见 §5 |
| B-6b | 调试面板可查看当日累计用量与**费用** |
| B-6c | **可设每日费用上限**（v0.1 修订：原为"每日 token 上限"）。达到上限后宠物明确提示并停止请求——**用户对钱敏感、对 token 没概念，按钱卡才有实际约束力** |
| B-6d | 工具结果回填前截断到 N 字符，避免一次请求把上下文撑爆 |
| B-6e | 保持系统提示词前缀稳定（配合 B-3.1 的时间注入方式），提高 DeepSeek 上下文缓存命中率（命中部分更便宜） |
| B-6f | 价格来自本地 `config/pricing.json` **手工维护**的价格表。**必须在文档与设置面板中写明：费用为估算值，随官方调价会失真，不保证与账单一致，仅供自用参考** |

- 默认每日费用上限由开发给一个保守值（如 ¥10/天），可改可关。
- 上限触发时**不是静默失败**：宠物明确说出来（符合 NONO 人格，先给结论），并保留"今天不再问"的状态直到次日或用户手动解除。

### B-7 可观测与日志【P0】

- 结构化日志（JSON Lines，按天滚动）：时间、事件类型、模型、token、耗时、技能名、错误码。
- 内存中只保留最近 500 条（环形缓冲），超出写文件（呼应 `PRD-Body-v0.md` §6.3）。
- 每个 turn 结束写一条汇总记录，供调试面板展示。

### B-8 错误处理【P0】

| 错误 | 表现 |
|---|---|
| 网络不通 | 宠物转 `error`，提示"连不上大脑"，自动重试 1 次 |
| API Key 无效 / 缺失 | 提示去设置里填 Key，**不反复重试**。启动时与请求时是**同一条链路的两个触发时机**，复用同一套提示逻辑（见 `PRD-Body-v0.md` W-7.2），文案由开发拟定 |
| 余额不足 / 限流 | 明确提示，指数退避，最多 3 次 |
| 技能执行失败 | 不中断对话，让模型解释"这个我暂时查不到" |
| 循环超步数 | 停止并输出已获得的部分结论 |
| 应用崩溃 | 写崩溃日志到 `logs/`，下次启动提示查看 |

## 5. 数据模型（v0 草案）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sessions` | id, title, created_at, updated_at | 会话分组 |
| `messages` | id, session_id, turn_id, role, content, created_at | 对话历史。**不含 token 字段**（见下方 C-2 修订） |
| `usage_log` | id, session_id, turn_id, model, tokens_in, tokens_out, cached_tokens, latency_ms, cost_est, **skill_names**, created_at | **成本与用量的唯一记账点** |

**C-2 修订：token 记账的单一来源**
原稿在 `messages` 和 `usage_log` 里都放了 `tokens_in/tokens_out`，两处记账必然不一致。现定死：

- **`usage_log` 是唯一的记账来源**；`messages` 表不再存 token。
- **补上"本轮调用了哪些技能"**：`usage_log.skill_names`（JSON 数组字符串，如 `["weather"]`；无技能调用则为空数组）。原稿 B-2 第 5 步要求记录这个信息，但表结构里没有字段。
- `turn_id` 同时出现在两张表，用于把"一次用户提问触发的完整循环（可能包含多轮模型往返）"关联起来——它也是 IPC 层丢弃串台 `brain:delta` 的依据（见 `PRD-Body-v0.md` W-9）。

**存储与归档**
- 采用 WAL 模式；单例连接；prepared statement 复用。
- **归档策略**：每月执行一次 `VACUUM` 与归档（把 `messages` 中 90 天前的记录导出后清理）。v0 数据量极小，实现上可以先只做 `VACUUM`。
- v1+ 再增：`memories`（长期事实）、`tasks`（定时任务）、`cache_market`（行情缓存）。建表语句里以注释形式**预留**位置，v0 不创建。

**C-3 修订：技能缓存的存放位置**
原稿没说清 weather 技能的 10 分钟缓存放在哪。现定死：

- **v0 天气缓存放在进程内存**（`Map` + TTL，主进程内），**不落 SQLite**。
- 理由：v0 数据量极小、零 IO、零 schema 变更；重启后缓存失效对体验无影响。
- 因此 `weather/skill.json` **不需要 `db:cache` 权限**（v0.1 已移除），只声明 `network:weather`。`db:cache` 权限保留在清单里供 v1+ 的行情技能使用。

## 6. 依赖与技术选型

### 6.1 直接依赖（刻意保持极简）

| 依赖 | 用途 | 备注 |
|---|---|---|
| `openai` | 调用 DeepSeek（OpenAI 兼容接口） | 省去手写 SSE 流解析 |
| `better-sqlite3` | 本地数据库 | 同步 API、性能好；**需为 Electron ABI 重建** |
| `@electron/rebuild` | 重建原生模块 | 开发依赖 |
| `zod` | 校验技能参数与配置 | 防止模型给出畸形参数 |
| `node:test` | 单元测试 | Node 内置，零依赖 |

### 6.2 刻意不引入

| 不引入 | 原因 |
|---|---|
| LangChain / LlamaIndex 类框架 | 依赖树巨大（几十上百包）、版本易碎、抽象难调试。本项目只需**几十行的工具调用循环**，自己写更小更快更可控 |
| `keytar` | 已停止维护；Electron 内置 `safeStorage` 零依赖即可 |
| winston / pino | 自写 JSONL 追加 + 环形缓冲足够 |
| 向量数据库 | v0 不需要；v1+ 用 SQLite FTS5 已够 |

### 6.3 原生模块的坑（提前知道）

`better-sqlite3` 是 C++ 原生模块，Electron 的 ABI 与系统 Node 不同，**首次安装与每次升级 Electron 后都需要 rebuild**，否则报 `NODE_MODULE_VERSION` 不匹配。

- 处理方式：`postinstall` 脚本自动执行重建。
- **降级预案**：v0 消息量很小，若重建反复出问题，直接退化为 **JSON 文件存储**（`messages.jsonl` 追加写），功能不受影响。这条写进实施计划作为 Plan B。

## 7. 资源占用分析

Brain 本身**几乎不额外吃内存**——它就是主进程里的一段 Node 代码：

| 项 | 量级 | 说明 |
|---|---|---|
| 代码与运行时开销 | +10–30 MB | 相对 Body 的 280–520MB 属于零头 |
| SQLite | 几 MB + 文件缓存 | 10 万条消息约几十 MB 磁盘 |
| 网络等待 | 不占 CPU | 流式接收是 IO 等待 |
| **主要成本** | **Token 费用**，不是内存 | 这才是 Brain 真正要控的"资源" |

**结论**：资源焦虑主要在 Body（Electron 双窗口，上限 500MB，见 `PRD-Body-v0.md` §6.1），Brain 不是问题。

### 7.1 Brain 侧泄漏风险点

1. 会话对象 / 消息数组无限增长 → 强制上限 + 落盘。
2. 未 abort 的流式连接 → 取消/超时/错误三路径都要 abort。
3. 定时器在任务删除后未清理 → v1+ 涉及。
4. SQLite 长事务 / 未关闭的 statement → 复用 prepared statement。
5. 日志对象在内存累积 → 环形缓冲上限 500 条。

## 8. 验收标准

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AB1 | 对话 | 中文提问能在 2s 内开始流式返回 |
| AB2 | **用户主动中断** | 生成中点「停止」，**1s 内**停止且连接释放。⚠️ 与 `PRD-Skill-v0.md` AS13（技能卡住 10s 超时强制中断）是**两个不同场景**，测试用例不要混 |
| AB3 | 人格 | 回复符合 NONO 语气规范，不出现"作为AI"式套话。**判定方式**：固化一份 **20 条人格回归语料**（天气 / 时间 / 闲聊 / 越界请求各 5 条），每次改 `persona.md` 跑一遍人工打分 |
| AB4 | 时间感知 | 问"今天几号"能正确回答（依赖**本轮 user 消息前置注入**的时间，见 B-3.1） |
| AB5 | 技能调用 | 问"上海天气怎么样"能自动调用天气技能并给出真实数据 |
| AB6 | 技能失败 | 故意让技能报错，对话不崩溃，模型能解释失败 |
| AB7 | 循环上限 | 构造死循环场景，5 步后自动中止（**用 mock provider，不烧真 token**） |
| AB8 | 记忆 | 关闭应用再打开，历史对话仍在，可继续追问上文 |
| AB9 | **密钥安全** | API Key 不在 `config.json` 明文、不在日志、不在界面明文；抓包确认请求头之外无 Key 泄漏 |
| AB10 | 零外流 | 飞行模式开启后，抓包确认**无任何**外部请求 |
| AB11 | 白名单 | 请求白名单外域名时被 `safeFetch` 拒绝并记日志 |
| AB12 | 成本可见 | 调试面板显示当日 token 与**费用**估算；**达到每日费用上限后停止请求并给出明确提示**（用 mock provider 验证，不靠真烧钱） |
| AB13 | 稳定 | 连续跑 **`pnpm soak`**（mock provider，24h 等效、100+ 轮）后内存增长 ≤ 20MB。**必须脚本化执行，不靠人工守夜** |
| AB14 | 单一记账 | 一轮问答后，`messages` 无 token 字段，`usage_log` **恰好一条**记录且 `skill_names` 正确 |

## 9. 为什么不拆独立后端（决策记录）

| 维度 | 单体（Brain 在主进程） | 拆出本地服务 |
|---|---|---|
| 延迟 | 进程内通信，微秒级 | 本地 HTTP/WS，毫秒级 |
| 内存 | 省一个进程 | 多一个运行时（若 Python，+80MB 起） |
| 复杂度 | 低 | 端口占用、进程守护、崩溃重启、版本匹配 |
| 打包 | 一份 | 需把运行时一起打进去，安装包更大 |

**结论**：自用工具，单体正确。唯一值得拆的理由是"必须用 Python 的某个库"——而 v0 的天气技能用公开 HTTP 接口即可（`PRD-Skill-v0.md` §6），**因此不拆**。

**保留的退路**：IPC 载荷按 JSON-RPC 风格设计，将来真要拆，只需把调用点从"函数调用"换成"发消息"。

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| DeepSeek API 变更 / 限流 / 涨价 | 功能中断或成本上升 | 适配层隔离供应商；v1+ 备选其他 OpenAI 兼容服务或本地模型 |
| 模型幻觉出"实时数据" | 用户被误导 | 强制：实时数据必须来自技能；技能不可用时明确说"查不到"，禁止编造 |
| 模型不守工具调用规范 | 参数畸形、乱调技能 | zod 严格校验；校验失败作为错误回填；单技能连续失败 2 次禁用 |
| 上下文过长导致变慢变贵 | 体验与成本双降 | 工具结果截断 + 历史窗口上限 |
| `better-sqlite3` 重建失败 | 开发受阻 | 降级为 JSON 文件存储（§6.3 Plan B） |
| API Key 泄漏 | 安全与费用事故 | 钥匙串 + 日志脱敏 + 错误信息不回显 + AB9 验收 |
