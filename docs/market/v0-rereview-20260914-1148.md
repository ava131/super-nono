## 2. R-1｜C-1 是错的：`node:sqlite` 支持 WAL，代码从未用过 `better-sqlite3`

### 评审原文

> **必须统一为 `better-sqlite3`**。理由：`node:sqlite` 在 Node 22 是实验性模块、**不支持 WAL**……**这是硬 bug**

### 实测证据

**① 代码从来没用过 `better-sqlite3`**

```
$ grep better-sqlite3 package.json
（无输出）
$ node -p "JSON.stringify(require('./package.json').dependencies)"
{}
```

`src/main/store/db.js` 第 12 行是 `import { DatabaseSync } from 'node:sqlite';`。

**② `node:sqlite` 支持 WAL**

在项目目录建一个库直接问它：

```

设 WAL 后 : {"journal_mode":"wal"}      ← 生效
WAL 文件生成了吗: ✅ 是
node 版本 : v24.19.0
```

把存储换成 `better-sqlite3` 意味着：装 C++ 原生模块 → 为 Electron ABI 重建 → 依赖从 0 变回 1。
而这**正是 M3 阶段刻意消灭的最大工程风险**（`SDD-v0` 的 changelog v0.3 记录了这次选型收敛）。

### 但评审确实抓到了一个真问题（只是归因错了）

## 3. R-2｜A-3 已经修了，但评审的下游推理仍然有效

### 评审原文

> `safeFetch` 用 `signal: AbortSignal.timeout(...)` **覆盖**了调用方传入的 signal

### 实测证据

`src/main/skills/egress.js` 第 80–83 行：

```js
const { timeoutMs = 60000, signal: outer, ...rest } = options;
const timeout = AbortSignal.timeout(timeoutMs);
// 关键：两个 signal 都要生效——调用方取消要立刻断，超时也要断
const signal = outer ? AbortSignal.any([outer, timeout]) : timeout;
```

`SDD-v0` §6.8 的示例代码也是修好的版本（第 524–525 行带 `AbortSignal.any`）。
评审读到的是 v0 原稿的描述。

### 但这条仍然要执行

评审的下游要求**与 signal 是否已修无关，且是对的**：

1. `scan` 在**每次循环前**检查 `signal.aborted`，中断即抛 `CANCELLED`；
2. **`CANCELLED` 与 `TIMEOUT` 必须区分**——否则用户点「停止」会看到"超时"文案。

补充一条现状：`agent.js` 已经把 `AbortError` 归一化成 `CANCELLED`，所以上层没问题；**缺的是技能内部的循环检查**（`market` 还没实现，实现时必须做）。

## 6. 我自己犯的错：第一版探针的方法论

**必须记录，因为它产生过一个看起来很可信的错误结论。**

| | 第一版 | 修正后 |
|---|---|---|
| 方法 | 连打 10 次，取中位数 | 先预热、再重复采样、只报中位与 P95 |
| 测得 | 中位 **3464ms** | 中位 **137–723ms** |
| 推出 | 20 只 scan = **69 秒** | 20 只 scan = **7–19 秒** |
| 后果 | 差点写进文档，并据此要求把 `timeoutMs` 提到 60s+ | —— |

**发现过程**：做了个隔离实验——同一个 URL 连续 20 次、逐次打印延迟：

```
1:539  2:154  3:135  4:136  5:134
6:137  7:128  8:222  9:202  10:126
11:118  12:160  13:143  14:131  15:135
16:211  17:141  18:132  19:129  20:234
前 10 次中位数 137ms  |  后 10 次中位数 141ms   → 无衰减
```

**结论：那 3.4 秒是网络抖动，不是东财的问题。**

**教训（已写进探针脚本头部的注释）**：

> **单次采样会被网络抖动彻底污染。** 必须预热 + 重复 + 只报中位/P95，**从不报单次值**。

## 7. 意外收获：一次真实的限流实验

跑探针期间累计发出约 **160 次请求**，结果是：

| 数据源 | 触发量 | 表现 | 性质 |
|---|---|---|---|
| **东财** | ~160 次 / 10 分钟 | `Empty reply from server`（TLS 通、HTTP 层直接断） | **硬封**，无重试语义 |
| **Yahoo** | ~40 次 / 2 分钟 | `HTTP 429 Too Many Requests` | **软限流**，标准重试语义 |

**这验证了评审 A-2，也验证了原 PRD §3.1「只做日线」的价值**：

- 正常使用是 **20 次/天**，离触发点有 8 倍以上余量；
- 但**开发期反复调试很容易撞上**（我就是）；
- 所以设计上必须：
  1. **缓存不是优化，是保护**（重复查询绝不重复出网）；
  2. **绝不激进重试**——被 429/断连后要退避，否则加深封禁；
  3. **被封时的措辞要诚实**：说"数据源暂时拒绝了请求，过会儿再试"，**不要**说"查不到这只股票"（那是两回事）；
  4. 开发调试**不要**反复打真实接口，用 fixture。

**⚠️ 附带影响**：**东财现在处于被封状态**，恢复时间未知（评审 §6 的探针第 5 项"是否触发限流"已由本次事故给出答案：**会**）。在它恢复前，任何依赖东财的验证都做不了。
