## 3. 自发发现的 5 个真问题

> 这 5 个都是**实现过程中**发现的，且**没有一个是靠"再读一遍代码"发现的**。

### 3.1 `maRelation` 的 `crosses` 键会缺失（测试抓出）

均线样本不足时 `continue` 跳过了赋值，导致 `crosses.ma60` 是 `undefined` 而非 `null`。
调用方会**把"算不出"和"没有穿越"混为一谈**。

**教训**：`undefined` 与 `null` 的差别在数据类接口里是**语义差别**，不是风格问题。
现在测试专门断言"键必须存在且为 `null`"。

### 3.2 复权因子方向写反（测试抓出）

我在文档与断言里写"因子序列应**不增**" —— 那是**后复权**的特征。
前复权以最新一根为基准，因子应随时间**不降**（10 送 10 → `[0.5,0.5,0.5,1,1,1]`）。

**教训**：**金融公式的方向性不能靠"看起来对"**。现在专门有一条测试
抓"做成后复权"（因子递减必须报警）。

### 3.3 两条规则互斥：`read_only` 与"必须缓存"（测试抓出）

- `market` 是 `read_only`（正确）
- PRD §12.1 要求它**必须缓存**（因为实测 160 次请求就把东财打封）
- 而写闸门规定"`read_only` 不许写 `ctx.store`"

**两条规则单独看都对，撞在一起就让缓存静默失效** → 每次查询都出网 →
用户当天被限流封掉。

**修法**：区分「**用户数据**」与「**私有缓存**」。判据是"读这个 namespace 的
作者是不是同一个技能"——写闸门要保护的是**别的技能会当作可信来源读的数据**
（如自选股），而私有缓存只有自己读写。新增 `ctx.store.cache` 子 API，
权限由显式声明的 `db:cache` 决定。

**教训**：**权限模型要按"影响面"划分，不能按"读/写"划分。**

### 3.4 表格打包算法（测试抓出）

`renderScanSummary` 第一版在循环里用"当前省略数"预留尾部空间，
**预留量随行数变化** → 769/800 的预算下只放下 14 行。

**教训**：**预算类算法的"看起来能放下"和"真的能放下"是两回事。**
现在用两遍法 + 列宽自适应，并断言"永不超限"。

### 3.5 正则把"拒绝预测"判成"预测"（测试抓出）

语料 C05 的**正确**回答是「我**不知道**下周会怎样」，
而禁止规则里有「下周会反弹」—— **两者字面都含「下周会」**。

**不处理这个，越守规矩的回答越容易被自家检查判为违规**，回归就变成"惩罚正确行为"。

**教训**：**内容审核类正则应先跑自己的"正确答案"语料**，否则会误伤。

## 4. 用户实测暴露的 3 个缺口（最有价值的一节）

**这 3 个全部是"测试通过了、但用户一用就发现"的。** 它们比 §3 的 5 个更值得记，
因为 §3 的问题测试能抓，这 3 个**测试结构上抓不到**。

### 4.1 ETF 完全查不到 —— `candidatesForCode` 漏了 5 个首位数字

代码首位映射表**只认 `6` / `0` / `3`**（个股）。ETF 是 `5`（沪）/ `1`（深）开头 →
直接返回空数组 → **在碰接口之前就被拒**。

**而东财完全支持 ETF**（实测 `510300` / `159915` / `588000` 都返回数据）。

**为什么测试抓不到**：`symbols.test.js` 里**一条 ETF 用例都没有**。
测试只覆盖了我"想到"的输入分支 —— **没想到的分支就是会漏的地方。**

**修法**：补全实证过的首位映射（`5`/`1`/`2`/`9`），新增 `classifyCode()`，补 23 个用例。

### 4.2 新上市的票查不到 —— 网络搜索**根本没实现**

内置表刻意只收龙头（§5.1 说明了理由），所以新股必然查不到。
而原代码在这种情况下只返回一句"需要联网搜索"，**但那条路是空的** ——
用户唯一的出路是背代码。

**为什么测试抓不到**：**"功能缺失"不是 bug，测试不会失败。**
单测测的是"实现了的东西对不对"，测不出"该有的东西没有"。

**修法**：实现东财搜索兜底，并设计三分支判定（精确命中 / 唯一且包含 / 多条让选）。

### 4.3 直接报代码时名字显示成代码（用户注意到）

`516350` → 输出 `516350（516350）`。而真名（芯片ETF易方达）**就在取回的数据里**，
只是没用。

**为什么测试抓不到**：断言只查了"有没有数字、格式对不对"，
**没查"这句话读起来像不像人话"**。

**修法**：取数后用 `meta.longName` 补一次（仅当名字仍是占位符时）。

## 6. 做得好的地方

### 6.1 先评审、再动手，且评审记录只读

三份评审文档（`v0-review-1135` / `v0-rereview-1148` / `v0-review-FINAL-1205`）
+ 执行清单，**全部保持原样不被修改**，后续修正走新文档。

好处很实在：**"当时为什么这么决定"没有丢**。例如 §5 的第 3 条错误，
在 FINAL 里被明确撤回并标注了原因，而不是悄悄改掉。

### 6.2 宁可留占位，也不猜 schema

东财解析器写完但 `available: false` 挂了很久，直到用户抓到真实响应。

**关键设计**：`parseKlineResponse` 有一道**强不变量自检**（`low ≤ open, close ≤ high`）。
我穷举了 4 个价格字段的 **24 种全排列**：

| 自检强度 | 放过的排列数 |
|---|---|
| 只查 `low ≤ high` | **18 / 24** |
| 查 `low ≤ open, close ≤ high` | **2 / 24**（互为 open/close 交换，数值等价） |

**这个穷举让"先写解析器、等实测再启用"成为安全选择** ——
字段顺序写错会被**必然抓住**，不会静默产出错数据。

### 6.3 测试纪律：不打真实接口

- 真实响应存成 fixture（`test/fixtures/`，含出处登记）
- 复权换算用**合成除权数据**验证（因为真实 fixture 恰好无除权）
- 抓取脚本自己也有 10 个单测（用本地桩服务）

理由：东财按请求模式限流，**开发期反复调试就会把 IP 打封**（实测 160 次即封）。

### 6.4 两档样本阈值（文档一致性修复）

文档说"MACD 不足 60 根要标注不可靠"，代码 34 根就**静默**给值。
改成两档：**算不出来就不给；算得出来但偏短就标注**。

真实效果（宇树，19 根）：

```
样本不足：MACD（需 ≥ 34 根，当前 19 根）；区间位置/分位（需 ≥ 250 根，当前 19 根）
样本偏短、数值相对不可靠：RSI（建议 ≥ 60 根，当前 19 根）
```

**既不假装"19 根也能给可信 MACD"，也不因为样本短就拒绝给任何信息。**

## 9. 留给下一次的教训

按"下次最该改"排序：

1. **写完功能，先自己当用户用一遍。**
   §4 的 3 个缺口全是"用户一用就发现"，而测试全绿。**测试通过 ≠ 能用了。**
   具体做法：交付前手动跑一遍**真实输入**（含 ETF、新股、只报代码）。

2. **测试要覆盖"输入空间"，不是"我想到的输入"。**
   ETF 漏掉的根因是首位数字只覆盖了 3 个值。下次遇到"按某个维度分支"的代码，
   **先把该维度的取值枚举出来**，再逐個写用例。

3. **"该有的功能没有"要靠清单查，不能靠测试。**
   拿 PRD 的验收表逐条对着**真实操作**核，而不是对着单测核。

4. **内容审核类正则，先跑自己的正确答案语料。**（§3.5）

5. **常量一旦跨模块，立刻单一来源。** 值相等时没有症状，等有人改一处才发现。

6. **证据分级要贯穿始终**，不只写在评审文档里。§5 的 4 次错都是"推断当事实"。
