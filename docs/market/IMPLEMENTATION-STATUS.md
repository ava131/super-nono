### 🔴 更正：封锁性质不是"地理封锁"（补充记录 §1 推翻了本文档初版的推理）

**本文档初版（12:20）写的判读**：

> "东财是**端点级应用层封锁**（非网络不通），**符合"境内源拒绝海外 IP"的特征**，"因此在 PM 的国内环境应可用""

**⚠️ 该推理已被补充记录（12:10）的进一步实测推翻。** 补充记录的证据：

| 测试 | 结果 |
|---|---|
| 同一主机的一个**不存在的路径** | **HTTP 404** ← 主机完全可达 |
| 同一主机的根路径 | HTTP 404 |
| **行情 API 路径** | HTTP 000 ← 只有这个路径被拒 |
| 换 3 个东财行情主机 | 全部 HTTP 000 |
| 东财搜索端点（另一台主机） | HTTP 200 |
| 距上次被封 25+ 分钟 | 仍未恢复 |

**时间线（同一台机器、同一个 IP）**：

| 时刻 | 状态 | 当时在做什么 |
|---|---|---|
| 11:40–11:46 | ✅ K 线可用（最快 137ms） | 探针第 1–3 轮 |
| 11:47 起 | ❌ HTTP 000 | 累计已发出约 **160 次**请求 |

**关键判读**：

> 主机可达（404 正常）+ 只有行情路径被拒 + **一小时前同一 IP 还能用**
> ⇒ **这是「路径级反爬」按「请求模式」触发，不是「按 IP 的地理封锁」。**

**这条更正的重要性（不是抠字眼）**：

**如果触发条件是请求模式而不是地理位置，那么国内同样会被触发。**
由此推出原判读低估了的风险：

> **`scan` 有可能把自己打封。**
> 正常使用 20 次/天有 8 倍余量；但只要出现一个缓存 bug（缓存键写错、TTL 失效、循环重试），
> 就可能在同一分钟内打出上百次请求 —— **然后用户当天彻底查不到行情，而且会以为是软件坏了。**

**已据此落实的改动**：

- PRD §12.1 限流纪律从 **4 条 → 5 条**，新增第 5 条「**出网次数自检**」（单次 `scan` 请求数 > 25 记 warn）——
  这是发现缓存 bug 的**唯一早期信号**
- PRD §12 新增风险行「**`scan` 把自己打封**」
- 该组纪律的定性从"注意事项"提升为「**核心安全属性**」

**结论不变**：M-0 仍要在国内跑。**但推理已改，风险定级已提高。**

#### 由此得到三条结论

**① "地理封锁"的判断是错的，终版 §2.1 的措辞要改。**
东财在**海外 IP** 上完全可用（`200` + 真实数据）。之前观察到的 `HTTP 000`

**② 主备顺序依然是"东财主 / Yahoo 备"，但理由变了。**

- 东财在**国内外都通**，且是 PM 的看盘软件（口径同源）→ **主源**
- Yahoo 是备源

**③ 真正的风险不是"哪个源通不通"，而是"两个源都会限流"。**

> **缓存不是优化，是保护。**（PRD §12.1 第 1 条）

这个答案不影响架构（主备顺序、缓存、节流都已按"会限流"设计），

### 实现的函数

| 函数 | 口径要点 |
|---|---|
| `sma(values, n)` | 简单移动平均；不足 n 根返回 `null` |
| `emaSeries(values, n)` | **种子 = 前 n 项 SMA**（与 TA-Lib / A股软件一致） |
| `rsi(values, period=14)` | **Wilder 平滑**；`avgLoss===0 → 100`；全平 → 50 |
| `macd(values)` | 12/26/9；**柱 = 2×(DIF−DEA)**（A 股惯例，MK5） |
| `volumeRatio(vols)` | 当日 ÷ 近 20 日均量，**不含当日**（评审 B-4 统一口径） |
| `rangePosition(values)` | `(P−min)/(max−min)×100%`，250 日 |
| `percentileRank(values)` | `count(close ≤ P)/N×100%`，250 日 |
| `volatility(values)` | 日收益率标准差 × √252，20 日 |
| `maRelation(bars)` | 价格与各均线上下关系 + 最近穿越天数 |
| `daysSinceCross(values, w)` | 最近一次穿越在几根 bar 之前 |
| `computeAll(bars)` | **快照唯一入口**：一次算出全部指标 + `insufficient` 清单 |

**参数集中在 `PARAMS` 并 `Object.freeze`** —— 改参数等于改验收口径，必须同步改文档（PRD §4 要求"参数写死"）。

### 测试覆盖的验收项

| 验收项 | 覆盖方式 |
|---|---|
| **MK4**（指标口径） | RSI 用**独立复算**逐位比对；EMA 种子、MACD 定义式均单独断言 |
| **MK5**（MACD 柱 ×2） | 断言 `histogram === 2×(dif−dea)`，容差 1e-12 |
| **MK13**（分位可复现） | 同一数据两次调用结果严格相等 |
| **MK16**（样本不足明说） | 每个指标都测了"不足 → `null`"；`computeAll` 的 `insufficient` 逐条列明 |

### ⚠️ 本模块**故意没有**做的事（重要）

1. **不硬编码任何"真实行情软件的精确数值"** —— 因为当前没有可核对的 fixture。
   MK4 的**真实对账**必须在有真实数据后做（终版 T-4：基准 = 东财，容差相对误差 1e-6）。
   **伪造精确期望值等于给自己放假**，故只断言数学恒等式与口径。
2. **不联网、不碰存储、不认识任何股票** —— 输入 OHLCV 数组，输出数值（SDD §4.3）。

### 测试暴露并修掉的真实 bug

| bug | 现象 | 修法 |
|---|---|---|
| `maRelation` 的 `crosses` 键缺失 | 均线样本不足时 `continue` 跳过了赋值，导致 `crosses.ma60` 是 `undefined` 而非 `null`，调用方会与"没有穿越"混淆 | 改为键**始终存在**，算不出显式给 `null` |

### 一个实现细节（防回归）

`computeAll` 里 `insufficient` 数组**必须在对象字面量外先声明**：

```js
/** @type {string[]} */
const insufficient = [];
const result = { ..., insufficient };
```

若直接写 `insufficient: []`，TS 会把它推断为 `never[]`，后续 `push(string)` 报 TS2345。

### 5.2 为什么不打网络也能做

用**真实抓包存档**（2026-09-14 11:59 从 `query2.finance.yahoo.com` 抓到，22 根茅台日线）。
三条纪律：

1. **fixture 是真实响应的存档，不是手编数据** —— 保住"真实 schema 兼容性"这个价值。
2. **fixture 在 `README.md` 里登记出处**（URL、抓取时间、抓取环境、根数）。
3. **开发调试一律用 fixture**（PRD §12.1 第 4 条）—— 实测已证明反复打真实接口会封 IP。

### 5.3 ⚠️ 真实 fixture 的一个局限（已显式标注）

该区间**恰好没有除权**，`adjclose === close` 全程成立（22/22），
因此它**验证不了复权换算是否真的生效** —— 只能验证"不换算时也不出错"、以及真实 schema 兼容。

→ **换算逻辑另用「带已知除权点的合成数据」验证**（`adjust.test.js` 的 `makeSplitScenario`）。
→ 两者缺一不可：只有合成数据会脱离真实 schema，只有真实数据则验证不了换算。
→ **MK3（真实除权案例）仍需在有真实除权标的时补做。**

### 5.4 🐛 实现过程中修掉的两个错误（都是我自己的）

| # | 错误 | 影响 | 修法 |
|---|---|---|---|
| 1 | **`checkFactorMonotonicity` 的因子方向写反了** | 我在文档与断言里写"因子序列应**不增**"——那是**后复权**的特征。前复权以**最新一根为基准**，因子应随时间**不降**（例：10 送 10 → `[0.5,0.5,0.5,1,1,1]`） | 改名 `checkFactorDirection`，断言改为"不降"，并**加了一条测试专门抓"做成后复权"**（因子递减必须报警） |
| 2 | `yahoo.js` 的 JSDoc union typedef 括号不配对 | `tsc` 报 TS1003；函数体本身没问题，是类型声明写坏了 | 拆成 `YahooSuccess` / `YahooFailure` 两个 `@typedef` 再 union |

### 5.5 已固化的不变量（防回归）

`adjust.test.js` 里锁定了两条跨分支不变量：

### 6.2 ⚠️ 一个刻意的范围决定：不做"320 条"

SDD-market §5.2 的目标是「沪深 300 + 主要指数 ≈ 320 条」。**我没有硬凑到 320 条，这是有意的。**

理由：**手写 320 个股票代码是危险行为**。股票代码是"从字面上看不出对错"的那类数据——
`600519` 抄错一位仍然是合法的 6 位数字，但会指向完全不同的标的。
而错代码**不会被任何本地校验发现**，只会让用户以为在查茅台、实际在查别的票。

**做法**：

1. 种子表只收**高置信度**条目（主要指数 + 各行业龙头，71 条），**宁可少不可错**
2. 表头写明**补全方式**（网络可用时用东财搜索批量生成 + 人工 diff）
3. 加**可由规则判定的校验**（代码首位 ↔ 市场一致性、symbol 拼写），
   至少让"把深市代码写到上交所"这类错误能被抓住
4. **代码本身是否真实存在，本地校验不了** —— 这需要联网核对，已在表头登记为待办

> **这是本阶段最重要的一条纪律**：种子表的价值是"降低出网次数"，不是"假装完整覆盖"。
> 表里没有的票走 `needs-network` 交给东财搜索，**功能不受影响**；但表里有错票，会直接误导用户。

### 6.3 🐛 实现中发现的两个真问题

#### (a) 指数与个股的代码规则**不同**

校验器第一版对**所有**条目套用"代码首位决定交易所"，结果 4 条指数全部报错：

```
❌ 000001.SH 上证指数 → code 000001 的首位指向 SZ，但 market 写的是 SH
```

**但数据是对的，校验器错了**：**指数用另一套代码分配**，上证指数就是 `000001.SH`（首位是 0 却在上交所）。

→ 给每条加 `kind: 'stock' | 'index'` 显式区分，**首位规则只校验个股**。
→ 这也是为什么 `kind` 要写成字段而不是靠"在哪个数组里"推断 —— 下游也用得到。

#### (b) `000001` 是真实的跨市场歧义

**`000001` 在沪深两市各自都有含义**：

| 符号 | 是什么 |
|---|---|
| `000001.SZ` | 平安银行（个股） |
| `000001.SH` | **上证指数**（指数） |

纯 6 位输入**无法区分**。这与"不许猜"原则直接相关，处理办法：

1. **先查表**：规则候选只是"可能属于哪些市场"，表里的条目是**确定的**。
   表里只收了上证指数 → 就返回它，无歧义。
2. **表里两个都有** → 返回 `ambiguous` + 候选，**让用户选**。
3. **表里都没有** → 也返回 `ambiguous`（附两个候选符号），不替用户决定。

→ 为此新增 `candidatesForCode()`（返回候选数组），并让 `codeToSymbol()`
在有多候选时返回 `null`。

**候选规则刻意保守**：只有 `0` 开头才给 `.SH` 备选（上交所 000xxx 指数系列）；
`30xxxx`（创业板）两边都在深市，**多给一个 `.SH` 只会制造假歧义**。

### 6.4 解析顺序（已实现，零出网优先）

| # | 来源 | 说明 |
|---|---|---|
| ① | **自选股本地表** | 最高优先级 —— 用户加过的票，他一定是在说它 |
| ② | **代码直通** | 6 位代码 / 带前缀 / 内部符号，唯一确定时不查表也能作答 |
| ③ | **内置种子表** | 名字、别名、代码、内部符号**全部参与精确匹配** |
| ④ | **模糊匹配** | 有候选就返回 `ambiguous` + 候选，**不自动选一个** |
| ⑤ | **`needs-network`** | 交给上层走东财搜索（Yahoo 搜索已实测不支持中文名） |

另外实现了 `toEastmoneySecid()`（**主源**寻址：SH=1 / SZ=0）与 `toYahooSymbol()`
（备源，位于 `sources/yahoo.js`：`.SH → .SS`）。

### 6.5 测试守的是什么

重点**不是"能不能解析对"，而是"不确定时是否老实返回候选"**——

因为猜错代码的代价不是"回答不准"，而是**用户以为在看 A 股、实际在看 B 股**。
所以专门有一组用例检查：歧义代码返回候选、北交所代码不猜成深市、
五位数港股代码不被当成 A 股、空/畸形输入不崩。

内置表本身也有 5 条自检用例（形状自洽、code 唯一、**name/alias 不跨条目重复**、
只含沪深、kind 合法）——表是数据，数据也要被测。

### 7.2 写闸门：命名空间隔离 ≠ 权限隔离

评审决定 9 的核心。`createSkillStore(namespace, manifest)` 按 **risk** 决定是否可写：

| risk | 可写 | 档位 |
|---|---|---|
| `read_only` | ❌ | L1 |
| `local_reversible` | ✅ | L1.5 |
| `local_write` / `external_send` | ✅ | L2 |
| 未知 / 缺 manifest | ❌ | **fail-closed** |

**为什么必须有**：只做命名空间隔离的话，`read_only` 技能照样能往**自己**的命名空间里写。
它写不进别人的，但**它自己的数据正是别的技能会当作可信来源读的东西**
（`market` 会读 `watchlist` 的自选股）。**"声明层面写死判定条件"解决不了越权调用。**

写被拒时**抛 `PERMISSION` 而不是静默忽略** —— 静默忽略会让"技能以为写成功了"这种 bug 拖很久才暴露。

三道约束：key 白名单、单值 64KB、**单命名空间 1MB**。
上限检查算的是**替换旧值后的净增量**，所以"把一个大值改小"不会被自己挡住。

### 7.3 🐛 实现中发现的两个真问题

#### (a) `KEY_PATTERN` 只允许小写，会拒掉**按文档写的缓存键**

我最初把 key 白名单定成 `^[a-z0-9_:.-]{1,64}$`（全小写）。
但 SDD-market §5.4 规定的缓存键是 `kline:{source}:{symbol}:{range}`，
而内部符号是**大写**的（`600519.SH`）→ **按文档写的键会被自己的校验拒掉**。

→ 放宽为 `^[A-Za-z0-9_:.-]{1,64}$`。真正的边界是"不能被 SQL/路径当成特殊字符"，
而这条已经排除了引号、空白、斜杠等一切危险字符。**测试抓出来的**。

#### (b) `ErrorCode` union 里缺了 4 个**已经在用**的错误码

`runner.js` 早就在 `fail('PERMISSION', …)` / `fail('BAD_ARGS', …)` / `DENIED` / `FORBIDDEN`，
但 `errors.js` 的 `ErrorCode` typedef 里没有它们 —— 因为 **`runner.fail()` 当时没标注返回类型**，
类型检查漏过了。`store.js` 用 `new AppError('BAD_ARGS', …)` 时立刻暴露。

→ 补齐 4 个码**并同步加进 `MESSAGES`**（`Record<ErrorCode, string>` 会强制这一点，
以后再加码就不能忘记配文案）。这是**既有的类型漏洞**，不是本次引入的。

### 7.4 L1.5 的 schema 规则修订（评审 C-2）

| 旧规则 | 新规则 |
|---|---|
| "`risk` 非 `read_only` 时**强制** `requiresConfirmation: true`" | "**L2 / L3 必须确认；L1.5 不得要求确认**" |

**后半句是重点**：如果 L1.5 也要求确认，那"加自选每次弹框"的问题就回来了 —— 而那正是
L1.5 要解决的问题。所以**显式禁止** L1.5 声明 `requiresConfirmation: true`，
并在错误信息里写清原因（否则后人会觉得这条校验莫名其妙）。

### 7.5 `watchlist` 的两个设计决定

**① 不出网 —— 这是刻意的，不是省事**

`skill.json` 的 `networkHosts` 是**空数组**，符号解析只查本地表 + 已加过的自选，
解析不到就**返回候选让人确认**（"你是说：五粮液(000858)？"）而不是静默联网。

两层理由：**架构上自洽**（它本就没有出网权限）；**体验上更好**
（数据源全挂时自选名单仍然可用 —— MK18）。

**② 测试刻意不提供 `safeFetch`**

`watchlist.test.js` 的 `ctx()` **不给 `safeFetch`**。这样如果哪天实现里偷偷发了网络请求，
测试会因缺少 `safeFetch` 而立刻暴露，而不是悄悄通过。

**③ 增删都是幂等的**

重复添加不报错（"已经在自选里了"），删不存在的也不报错（"本来就不在"）。
自选股操作不该因为"你已经做过了"而变成一个吓人的错误。

### 7.6 测试守的是什么

- **写闸门**：`read_only` 技能写会抛错、但**仍可读**；未知 risk **fail-closed**；
  缺 manifest **fail-closed**
- **上限**：刚好 20 支能加满，第 21 支被拒不挤掉已有的；改小一个值不被 1MB 上限挡住
- **不猜**：解析不到时**返回候选且不写入任何东西**（失败的添加不能留痕）
- **零出网**：没有 `safeFetch` 也能完成 add/list/remove
- **健壮性**：库里存了畸形数据时 list 过滤掉坏条目而不是崩

### 8.2 🐛 本轮最重要的发现：两条规则撞在一起

**`market` 是 `read_only`（正确），但 PRD §12.1 又要求它必须缓存。**
而 P3 刚加的写闸门规定"`read_only` 技能不许写 `ctx.store`"——于是缓存**静默失效**：

```
[nono:warn] store.denied { namespace: 'market', op: 'set', risk: 'read_only' }
```

**后果链条**：缓存失效 → 每次查询都出网 → **`scan` 一次打 20 个请求** →
用户当天被数据源限流封掉（实测 ~160 次就硬封）。

**两条规则单独看都对，撞在一起就出事。**

**修法：把「用户数据」与「私有缓存」当成两种东西。**

判据是"**读这个 namespace 的作者是不是同一个技能**"：

- 写闸门要保护的是**别的技能会当作可信来源读的数据**（如 `watchlist` 的自选股，`market` 会读）
- 一个技能的私有缓存**只有它自己读写**，污染自己的缓存影响不了任何人

所以新增 `ctx.store.cache` 子 API，权限由**显式声明的 `db:cache`** 决定：

| 场景 | 用户数据（`set`） | 私有缓存（`cache.put`） |
|---|---|---|
| `read_only` 且未声明 `db:cache` | ❌ | ❌ |
| `read_only` 且声明了 `db:cache`（就是 `market`） | ❌ | ✅ |
| `local_reversible`（`watchlist`） | ✅ | ✅（若声明） |

**这不是给 `read_only` 开口子**，而是承认两者性质不同：`read_only` 约束的是"不改用户状态"，
而缓存是**它自己的**临时数据。

### 8.3 顺带修掉的架构问题：插件不该 import 宿主内部

第一版从 `skills/market/*.js` 里 `import log from '../../src/main/log.js'`，结果：

1. **相对深度依赖目录结构** —— 不同层级要不同的 `../` 数，本轮就写错过两次
2. **破坏插件契约** —— 技能能 import 宿主内部，就等于能绕过 `ctx.safeFetch` 的白名单，
   而那正是 `PRD-Skill` §4.3 想避免的

→ 改为**注入式 logger**（`skills/market/log.js` 的 `createLogger(ctx)`）：
有 `ctx.log` 就用它，没有就 no-op（单测里正是如此，于是测试输出保持干净）。
**技能现在只依赖自己被注入的能力。**

### 8.4 东财适配器：**故意留成占位**

我没有东财 K 线的真实响应，**因此不写解析器**。这不是偷懒——本项目已经吃过两次亏：
`node:sqlite` 是否支持 WAL（我猜不支持，实测支持）、Yahoo 搜索是否支持中文股票名
（我猜"待实测"，实测完全不支持）。

意味着用户看到错的数字并据此判断 —— 比直接报错严重得多。

占位实现明确返回 `UNAVAILABLE`，并在文件头部写清：

### 8.6 🐛 表格打包算法修过一个 bug

### 9.2 架构决定：约束块由**注册表**提供，不由 persona 去查

第一版让 `persona.js` 直接 `import '../../../skills/market/prompts.js'`。问题：

1. **目录深度耦合** —— 相对路径本轮已经写错过两次
2. **层与层糊在一起** —— 新增技能要改 Brain 的代码，违反"加技能只加目录"

→ 改为：**注册表**（唯一知道"有哪些技能"的地方）提供 `describeConstraints(skills)`，
经 `agent.js` 传给 `persona.stablePrefix(skills, skillConstraints)`。
**Brain 层不再需要知道 `skills/` 的目录结构。**

**稳定性已验证**：两次调用 system 消息**逐字节相同**（1189 字符），
且块内**不含任何日期/时间** —— 否则 DeepSeek 前缀缓存会失效（PRD-Brain §B-6e）。

### 9.3 为什么约束写成**结构化数据**而不是散文

约束要同时喂给两个消费方：**模型**（要一段禁止清单）和**测试**（要机器可判定的清单）。

如果只写散文，测试就只能复制一份关键词列表，**两份会慢慢长歪**——
改了一处忘了另一处，回归就变成"看起来在跑、其实没在测"。

所以 `PROHIBITIONS` 是唯一事实来源，提示词与测试**消费同一份数据**。
测试里有一条专门验证"**每一类禁止项都至少被语料覆盖到**"和"**每个正则都真的能命中东西**"。

### 9.4 🐛 本轮抓到的三个真问题

#### (a) 正则把"拒绝预测"误判成"预测"（最严重）

语料 C05 的**正确**回答是「我**不知道**下周会怎样」——
而禁止规则里有「下周会反弹」这类**预测**。两者字面都含「下周会」。

**不处理这个，越守规矩的回答越容易被自家检查判为违规** ——
回归就变成"惩罚正确行为"。

→ 新增**否定语境**判断（`NEGATION_WORDS` + `isNegated`）：
模式命中处前面 8 个字符里若有「不知道 / 不能 / 无法 / 不给…」，则不算违例。

#### (b) 两条模式漏了真实说法

- 「现在**适合买入**」—— 不含"建议"二字，但同样是买卖指令 → 补 `(适合|时候|时机)(买入|卖出…)`
- 「**可能会跌**」—— 概率措辞同样在预测方向 → 补 `(可能|或将|有望)(涨|跌…)`
- 「现在**可以买入**」—— `可以…` 那一支漏了"买入/卖出" → 补全

#### (c) "源被拒"与"股票不存在"混为一谈 —— 关键词黑名单抓不到

语料 C13 的坏样本「查不到这只股票」（实际是**被限流**）**不含任何买卖建议**，
所以措辞黑名单抓不到它。但它的危害很实在：
**用户会以为代码写错了，反复重试，反而把封禁拖更久。**

→ 新增 `FAILURE_WORDING` 规则 + `checkFailureWording()`：
"源被拒"必须说"过会儿再试"、**不得**说"查不到"；反过来"确实不存在"才可以明说查不到。
这条同时进了提示词（`### 失败时怎么说` 一节）。

### 9.5 语料回归的**双轨**设计（评审 T-2）

| 轨 | 覆盖 | 说明 |
|---|---|---|
| **自动化** | 20 条语料的 `badSample` 必须被对应检出门抓到；`goodSample` 不得误报 | 三道门：措辞黑名单 / 数字溯源 / 失败措辞 |
| **人工打分** | 真问一遍 `question`，人读回答 | **不能省** —— 纯自动回归会漏掉"换个说法给建议" |

语料 20 条覆盖：索要建议 / 预测 / 正常解读 / 样本不足 / 源不可用 / 越界 / 自选操作，
其中**高危场景 10 条**（约一半）。

**有一条测试专门保证"坏样本要按它的坏法被抓"**：
措辞类（`refuse-*`）必须被黑名单抓到，编造类（`不得编造`）必须被数字溯源抓到——
这样"语料声明的期望"与"检测器实际做的"不会脱节。

### 9.6 数字溯源（评审 T-3）

`checkProvenance(answer, facts)`：答案里的每个数字都必须在**工具返回的事实文本**里找得到出处。

允许三类"可推出"的数字：**原样出现**、**四舍五入变体**、**由两个事实数算出的比率**（涨跌幅）。

已验证能抓到语料里编造的数字（`1800` 目标价、`60%` 分位、`12.34` 价格），
且不误报合法的四舍五入与日期。

⚠️ 它**不是**证明"没幻觉"，而是**把可疑点缩小到可人工复核的范围**。

## 13. 东财主源：从占位到启用

### 13.1 启用前：为什么先留占位（这不是"猜 schema"）

我仍然没有可存盘的完整响应体（唯一那次成功输出被截断，之后即被限流）。
但**把猜测面压缩到了一个常量**，并用已确证的部分兜住：

**已实测确证**（2026-09-14，唯一那次成功响应）：

- 外层形状：`{rc, rt, svr, lt, full, data:{code, market, name, klines}}`
- `rc === 0` 表示成功
- `klines` 是**逗号分隔的字符串数组**
- 每根**前两个字段是 `日期, 开`**（`2026-09-10,1291.00`）
- `data.market`：1=沪 0=深

**唯一还靠推断的**：`fields2` 里**收 / 高 / 低 / 量 的顺序**。

→ 把它抽成 `FIELDS2` 常量。**验证 = 改一个字符串 + 看一眼断言**，不用重读解析逻辑。

### 13.2 🔑 关键设计：**顺序写错不会静默产出错数据**

`parseKlineResponse` 里有一道**强不变量自检**：`low ≤ open, close ≤ high`。
不满足的行被**丢弃**，全部不满足则整体失败并提示"字段顺序可能不匹配"。

**为什么必须用强不变量**——我用实测那一根的真实数值穷举了 4 个价格字段的 **24 种全排列**：

| 自检强度 | 放过的排列数 | 结论 |
|---|---|---|
| 只查 `low ≤ high` | **18 / 24** | 基本拦不住 |
| 查 `low ≤ open, close ≤ high` | **2 / 24** | ✅ 只剩互为 open/close 交换的那一对（数值上等价、无法区分） |

**这个穷举是本轮最有价值的产出**：它把"顺序写错"从"可能静默出错"
变成了"**必然被抓**"，于是"解析器先写好、等实测再启用"才是安全的选择。
上表已固化成测试（`test/unit/eastmoney.test.js`，**30 个用例**）。

**诚实记录的残余风险**：那 2 种放行的排列只差 open/close 互换。
`high`/`low`/`close` 的语义都正确 → **对均线 / RSI / MACD / 分位没有影响**
（它们全部基于收盘价），只有 `open` 会错。已在测试里显式说明。

### 13.3 顺带解决的一个单位坑：手 → 股

东财成交量单位是**手**，Yahoo 是**股** —— 不换算的话 `量比` 会差 100 倍。
已加 `SHARES_PER_LOT = 100` 并在解析时统一成股。

（`量比` 本身是两个同单位量相除，所以**即使忘了换算它也不会错**；
但两条路径的 `volume` 语义不一致会在别处埋雷，所以统一掉更好。）

### 13.4 时区已对齐（两条路径不会差一天）

`dateToUtcSeconds()`（东财）与 `cache.toCnDate()`（Yahoo）
**互为逆运算**，已用 5 个跨年/闰日日期验证往返一致。

## 14. 二次自查：发现并修掉一处**文档与代码不一致**

### 14.1 问题：MACD 的"最小样本"两边说的不是一个数

| 出处 | 说法 |
|---|---|
| `PRD-market` §4 指标表 | MACD 最小样本 **60** |
| `SDD-market` §5.3 | "`N < 60` → MACD **标注不可靠**" |
| **代码** | `MIN_SAMPLES.MACD = 34` → **`N < 34` 才返回 `null`，34–59 静默给值** |

**22 根时看不出问题**（两边都是"没有 MACD"），但 **40 根时**：
代码给出一个 MACD，而文档认为它"不可靠"——**而代码从不标注**。

**静默的那一侧更危险**：用户以为它和 60 根时一样可信。

### 14.2 修法：把"算不出来"与"算得出来但偏短"分成两档

两档回答的是**不同问题**，之前被混成了一个数：

| 档 | 判据 | 行为 |
|---|---|---|
| **算不出来** | `N < MIN_SAMPLES` | **不输出**（`null`）+ 进 `insufficient` |
| **算得出来但偏短** | `MIN_SAMPLES ≤ N < RELIABLE_SAMPLES` | **照常输出** + 进 `unreliable`（标注"相对不可靠"） |

新增 `RELIABLE_SAMPLES`（MACD/RSI/量比/波动率 = 60，对齐 PRD 的"建议样本"），
`computeAll` 多返回一个 `unreliable[]`，`renderOverview` 多渲染一行。

**实测效果**（用真实 Yahoo fixture，22 根）：

```
样本不足：MACD（需 ≥ 34 根，当前 22 根）；区间位置/分位（需 ≥ 250 根，当前 22 根）
样本偏短、数值相对不可靠：RSI（建议 ≥ 60 根，当前 22 根）；量比（建议 ≥ 60 根，当前 22 根）；波动率（建议 ≥ 60 根，当前 22 根）
```

既不假装"22 根也能给可信 MACD"，也不因为样本短就拒绝给任何信息 ——
用户至少知道**它为什么不可靠**。

### 14.3 文档同步

- `PRD-market` §4 表头 `最小样本` → **`建议样本`**，并补一张两档对照表
- `SDD-market` §5.3 重写为两档规则（写明 34 / 60 两个数）
- 新增 6 个单测锁住两档关系（含"40 根时 MACD 必须进 `unreliable`"）

### 14.4 顺带完成的一次**真实数据端到端**验证

用真实 Yahoo 抓包跑通 `解析 → 复权 → 指标 → summary` 全链路：

```

数据截至 2026-09-14 收盘
现价 1278.50　涨跌 +0.26%
均线 MA5 1287.79　MA10 1298.09　MA20 1297.59
RSI(14) 35.5
量比 0.34（对前 20 日均量）
年化波动率 16.9%
```

**这是第一次用真实数据验证整条链路**（此前单测都用 mock 或合成数据），
也正因为看到了真实输出，才发现了上面那处标注缺失。

## 15. 第三轮自查：验证主备编排**真的会切**

前两轮自查都在"读代码找不一致"。这一轮换了个角度：**主动去戳那条从未被验证过的关键路径**。

### 14.1 发现：主备降级路径**从未被端到端验证过**

`market.test.js` 里关于降级的用例，实际上都落在"东财 `available: false`"这条路上 ——
也就是说，**"东财可用时优先用它"这个核心行为，一次都没跑过**。

这正是最该验的：主备顺序（评审决定 1）是数据源方案的全部意义所在。

### 14.2 验证结果（把东财临时置为可用）

| 场景 | 结果 |
|---|---|
| 东财可用 | ✅ `source: eastmoney`，**只请求 `push2his.eastmoney.com`，Yahoo 零调用** |
| 东财失败 | ✅ **整体切到备源**（`switched: true`），请求序列 `eastmoney → yahoo`，输出标注 `yahoo` |
| 复权口径 | ✅ 东财 `adjustedAlready: true`（跳过 `adjust.js`）；Yahoo `false`（必须自己换算） |

顺带确认了一个实现细节：`SOURCES` 是 `Object.freeze` 的（防误改），
但**单个适配器对象没冻结** —— 所以那个"等实测确认后只需把 `available` 改成 `true`"
的开关是**真的能拨动**的，不是我嘴上说说。

### 14.3 已固化成 4 个永久测试

关键是**用 `withEastmoneyEnabled()` 临时翻转开关再还原**，
这样"主源路径"从此**总在测试覆盖里**，不会等到真去抓数据时才发现问题。

### 14.4 附带确认：强不变量**不会误伤合法数据**

我在 §12.2 加的 `low ≤ open, close ≤ high` 自检，理论上有个风险：会不会把
**涨停 / 停牌复牌**这类极端行情误判成"字段顺序错"？

实测 7 种极端情形（一字涨停/跌停、涨停开盘后回落、跌停开盘后反弹、
停牌复牌价差极大、开盘即最高收盘即最低…）**全部被正确接受**。

原因是这条不变量**不是经验假设，而是数据定义上的恒等式**：
`high` / `low` 的定义本身就是"当天**包括开盘与收盘在内**的最高/最低价"。
已固化成测试。

## 16. 交付后自查：把"会漂移的常量"钉死

P0–P6 全部落地后做了一次一致性复查，找到**一类真实的隐患**。

### 16.1 问题：同一个契约常量有**两份定义**

| 常量 | 原本的两处 | 不一致的后果 |
|---|---|---|
| `SUMMARY_LIMIT` | `runner.js`（**截断**）与 `snapshot.js`（**排版**）各写 `800` | 排版以为能放 800、实际被截到别的数 → **用户看到残缺数据且毫无提示** |
| `WATCHLIST_LIMIT` | `watchlist`（**写入**判上限）与 `market.scan`（**读取**判上限）各写 `20` | 能加 30 支但 `scan` 只接受 20 → **用户加了却扫不了** |
| `FETCH_WARN_THRESHOLD` | `cache.js` 写 `25` | 调整自选上限时忘了同步 → 出网自检误报，或**失去发现缓存 bug 的唯一早期信号** |

**当前值恰好相等，所以不会有立即可见的问题** —— 这正是它危险的地方：
将来只改一处，问题会在很远的地方以"数据看着不对"的形式冒出来。

### 16.2 修法：单一来源 + 防绕过

新增 `shared/limits.js`（**零依赖纯常量模块** —— 技能与宿主都要能安全引入），
三处定义各自改为 `= LIMITS.XXX`，**保留原有的导出名**，因此消费方一行不用改。

新增 `test/unit/contract.test.js`（**9 个用例**），做两件事：

1. **运行时值一致**：断言 `runner.SUMMARY_LIMIT === snapshot.SUMMARY_LIMIT`（同理 watchlist/market）
2. **静态唯一来源**：扫源码断言这些常量**只在 `shared/limits.js` 里以字面量出现** ——
   只比运行时值是不够的：两份字面量恰好相等时测试会通过，**隐患仍在**

还顺带锁了一条设计规则：**技能目录里不许 import 宿主内部模块**（`src/main/`）。
这是为了守住插件契约 —— 技能一旦能 import 宿主内部，就能绕过 `ctx.safeFetch` 的白名单。

> ⚠️ 这条静态检查第一版**误报**了：`skills/market/log.js` 的文档注释里
> 写着一个 `import '../../../src/main/log.js'` 的**反例**（用来解释为什么不该这么写）。
> 修法是扫描前先剥掉注释 —— **静态检查也要能区分"示例"与"实际代码"**。

### 16.3 顺带确认的两件事（复查结论：无问题）

| 检查项 | 结论 |
|---|---|
| 声明域名 vs 实际请求域名 | ✅ 一致。`yahoo.js` 用 `query1.finance.yahoo.com`，与 `skill.json` 白名单相符（我一度以为它用了 `query2`，那是注释里的历史记录） |
| `watchlist` 声明了 `db:cache` 但没用 | ✅ 无功能影响。它只影响 `cacheWritable`，用户数据路径走 `local_reversible` 的 `.writable`，两者独立。属于"声明宽于所需"，不是缺陷 |
