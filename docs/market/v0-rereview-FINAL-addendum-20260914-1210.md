## 1. 🟠 决定 1 的「地理封锁」推断，证据不支持

### 终版的说法

> 我在当前（海外）网络下实测**东财 K 线端点不通**（`HTTP 000`，TLS 握手成功但服务器主动断开），这**符合"境内源封海外 IP"的预期**，因此**在国内（PM 的实际使用环境）应当可用**。

### 新的实测证据（2026-09-14 12:00–12:10，比终版晚 5–10 分钟）

```
① 同一主机的一个不存在的路径   → HTTP 404        ← 主机完全可达
② 同一主机的根路径             → HTTP 404        ← 同上
③ 同一个行情 API 路径          → HTTP 000        ← 只有这个路径被拒
④ 换 3 个东财行情主机          → 全部 HTTP 000
     push2his.eastmoney.com / push2.eastmoney.com / 92.push2his.eastmoney.com
⑤ 东财搜索端点（另一台主机）    → HTTP 200        ← 正常
⑥ 距上次被封已 25+ 分钟         → 仍未恢复
```

**关键点：主机是可达的（404 能正常返回），只有行情 API 这个路径被单独拒绝。**

这是**路径级反爬**的典型特征，不是"按 IP 的地理封锁"：

| 如果用地理封锁解释 | 实测 |
|---|---|
| 海外 IP 应该整个主机不可达 | ❌ 主机可达，404 正常 |
| 应该所有东财服务都拒 | ❌ 搜索端点 200 正常 |
| 一小时前为什么能用？ | ❌ 解释不了（同一台机器、同一个 IP） |

**时间线**（全部来自本机实测）：

| 时刻 | 状态 | 当时在做什么 |
|---|---|---|
| 11:40–11:46 | ✅ K 线可用（多次成功，最快 137ms） | 探针第 1–3 轮、合并版 |
| 11:47 起至今 | ❌ HTTP 000 | 累计已发出约 **160 次**请求 |

### 为什么这条重要（不是抠字眼）

**如果触发条件是"请求模式"而不是"地理位置"，那么国内同样会被触发。**

由此推出一个终版没有强调的风险：

> **`scan` 有可能把自己打封。**
> 正常使用是 20 次/天，离触发点有 8 倍余量；但只要出现一个缓存 bug（缓存键写错、TTL 失效、循环重试），
> 就可能在同一分钟内打出上百次请求——**然后用户当天彻底查不到行情，而且会以为是软件坏了。**

**所以 A-3 的四条限流纪律，严重性要从"注意事项"提升为"核心安全属性"**，并且应当补一条：

> 5. **必须有"出网次数自检"**：单次 `scan` 的实际请求数超过预期（如 >25）时记 warn 日志，
>    因为那意味着缓存没生效——**这是发现缓存 bug 的唯一早期信号**。

**行动不变**（M-0 仍要在国内跑），但**推理要改**，否则会低估限流风险。

## 2. 🟠 M-0 的验证命令可能给出假阴性

### 终版给的命令（§6 A-2）

```bash
curl -s -m 12 -o /dev/null -w "HTTP %{http_code} / %{time_total}s\n" \
  "https://push2his.eastmoney.com/api/qt/stock/kline/get?secid=1.600519&fields1=f1&fields2=f51,f53&klt=101&fqt=1&lmt=3"
```

**两个问题：**

| # | 问题 | 后果 |
|---|---|---|
| 1 | 参数是 `fields1=f1`（**单字段**）。本机所有**已知成功**的请求用的都是 `fields1=f1,f2,f3` | 若 `f1` 不足，**国内也会返回错误** → 误判为"东财不通" → 整个数据源方案被错误推翻 |
| 2 | `-o /dev/null` **丢掉了响应体** | 即使返回 `HTTP 200` 但 `data` 为空（东财对异常参数就这德行），也会被判为"通过" |

**这不是苛求——M-0 是终版自己说的"唯一可能推翻数据源方案的变量"，而它的判据本身没被验证过。**

### 建议改用（同时校验状态码与内容）

```bash
curl -s -m 12 \
  "https://push2his.eastmoney.com/api/qt/stock/kline/get?secid=1.600519&fields1=f1,f2,f3&fields2=f51,f53&klt=101&fqt=1&lmt=3" \
  | head -c 300
```

**判据**：
- ✅ 通过：输出里能看到 `"klines":["2026-..."` 这样的内容
- ❌ 不通：空输出，或 `curl: (52) Empty reply from server`
- ⚠️ 其它：把完整输出贴出来再判断

## 5. 🟡 两个设计缺口（终版没提，但会影响实现）

### (a) 降级判据未定义 → 可能导致「同一次 scan 混源」

决定 1 定了主备，但 `SDD-market` §5.6 的降级流程图**只画了顺序**（东财 → Yahoo → 报错），**没有定义"什么时候算东财失败"**：

- 一次超时？
- 一次 429？
- 一次 `Empty reply`？
- 连续两次失败？

**如果不定义，最坏情况是**：scan 扫 20 只，第 7 只时东财偶发失败 → 切到 Yahoo → 第 8–20 只来自 Yahoo。

**后果**：同一次 scan 里，7 只票用东财前复权基准、13 只用 Yahoo 前复权基准，**两组数值不可直接比较**（这正是 PRD §4 与 T-4 一直在防的事）。

**建议**：

1. 定义判据：**首次请求失败即整体切换**（不是每只单独降级）；
2. **同一次 `scan` 内不换源**——一次工具调用的结果必须来自同一个源；
3. 输出里标注本次实际使用的源（已有要求，这里补上"整批同源"的语义）。

### (b)「早失败」是性能必需品，不是优化

如果降级判据是"每只票等满超时才失败"，那么：

```
20 只 × 10s 超时 = 200 秒
```

而 `scan` 的 `timeoutMs` 是 **45s** → **超时会在扫到第 5 只时就触发**，用户拿到一个残缺结果。

**建议明确写成实现要求**：

> **首次请求用短超时（2–3s）快速失败并整体切源**，而不是每只都试满 10s。
> 宁可"2 秒内换源成功"，不要"每只各等 10 秒然后整体超时"。

### (c) MK4 / MK5 在备源路径下必然不成立

| 验收项 | 内容 | 问题 |
|---|---|---|
| MK4 | 指标数值与公开行情软件逐项一致 | 基准 = 东财（T-4） |
| MK5 | MACD 柱口径与 A 股行情软件一致 | 同上 |

**但备源走 Yahoo，前复权基准不同** → 均线/MACD 数值会有已知偏差 → **这两条在 Yahoo 路径下必然失败**。

**建议**：

- MK4 / MK5 明确限定为「**东财路径下**」；
- 新增一条：**备源路径必须在输出里标注数据源**，且验收标准改为"数值与 Yahoo 官方图表一致"（而不是与东财一致）。
