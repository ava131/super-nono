### 决定 1 — 数据源：**东财为主源，Yahoo 为备源**【已决 · 由 PM 的"在国内用"确定】

**PM 原话**：

> 在国内用。我就今天在国外。

**这条信息是决定性的。** 结合实测证据，主备顺序确定为：

| 角色 | 数据源 | 理由 |
|---|---|---|
| **主源** | **东财** `push2his`（`fqt=1`） | PM 在**国内**长期使用；东财是境内源，国内快且稳定 |
| **备源** | **Yahoo** chart API | 当前海外环境下**实测完全可用**；国内环境下可能不可达，作为降级路径保留 |

**必须诚实标注的两个不确定性**（见 §0.1 证据等级）：

1. **【待验证】东财在国内是否真的通**——我在当前（海外）网络下实测**东财 K 线端点不通**（`HTTP 000`，TLS 握手成功但服务器主动断开），这**符合"境内源封海外 IP"的预期**，因此**在国内（PM 的实际使用环境）应当可用**。**但这一步没有被任何人实测过**，因为当前环境测不了。→ **列为 M-0 第一步验证。**
2. **【推断】Yahoo 在国内大概率不可达**——Yahoo 服务在中国大陆长期不可直接访问，属公开常识，但**未针对 `query1.finance.yahoo.com` 实测**，且不同网络/时点可能不同。→ **因此备源的价值是"出国时可用"，不是"国内容灾"。**

**⚠️ 由此得出一个必须写进 PRD 的结论**：

> **在国内的正常使用场景下，东财实质上是唯一源。**
> 备源 Yahoo 只在海外网络下起作用。**所以"东财挂掉"在国内等于"今天查不到行情"** —— 这不是设计缺陷，是必须如实告知用户的能力边界。

**这与原 PRD §12 的应对措辞不同**：原文写"主备双源 + 失败如实报错"，暗示双源能保命。**应改为**"境内单主源 + 海外备源；国内主源不可用时明确告知，不装作有备份"。

**连锁影响（与原方案相反）**：

| 项 | 原方案（1135 版评审的决定 2） | **终版** |
|---|---|---|

**特别提醒**：1135 版评审把 §5.1 的删除当成"收益"，**这是错的**——那是"M-1（Yahoo 单源）方案"的代价，不是收益。**在双源方案下，§5.1 是 Yahoo 路径的必要步骤，必须保留且必须实测。**

### 决定 8 — `SDD-v0` 的过时残留：**改文档，不改代码**【已决】

**这是 1135 版评审造成的最大风险，必须显式纠正。**

**1135 版评审的错误主张**：

> "`node:sqlite` 在 Node 22 是实验性模块、**不支持 WAL**……**必须统一为 `better-sqlite3`**……**这是硬 bug**"

**实测反驳（【实测·本机】，2026-09-14）**：

```bash
$ node -v
v24.19.0

$ node -e "
const {DatabaseSync}=require('node:sqlite');
const db=new DatabaseSync('/tmp/wal_test.db');
console.log('设WAL前:', JSON.stringify(db.prepare('PRAGMA journal_mode').get()));
console.log('设WAL后:', JSON.stringify(db.prepare('PRAGMA journal_mode=WAL').get()));
"
设WAL前: {"journal_mode":"delete"}
设WAL后: {"journal_mode":"wal"}      ← 生效
```

**结论：`node:sqlite` 支持 WAL。1135 版评审的该主张不成立。**

**并且代码从未用过 `better-sqlite3`**：

```bash
$ node -p "JSON.stringify(require('./package.json').dependencies)"
```

**1135 版评审的 B-4 方向正确，但定性需修正。**

**A-1｜复权方案随数据源反转，§5.1 必须保留**

- **正确处置**：`SDD-market` §5.1「复权因子换算」**保留**，因为它服务的是 **Yahoo 备源路径**（Yahoo 返回原始 OHLC + `adjclose`，必须自己换算）。
- 东财路径不需要它（`fqt=1` 直给），所以 §5.1 开头应写明：**"本节只适用于 Yahoo 路径；东财路径跳过。"**

**A-2｜东财 K 线在国内是否可用，是 M-0 第一步必须验证的事**

- **【待验证】**：当前环境测不了。**PM 在国内机器上一跑就知道。**
- 若国内也不通 → **回到 Yahoo 单源 + 讨论代理**（那就变成另一个方案，需重新评审）
- **验证方法（1 分钟）**：
  ```bash
  curl -s -m 12 -o /dev/null -w "HTTP %{http_code} / %{time_total}s\n" \
    "https://push2his.eastmoney.com/api/qt/stock/kline/get?secid=1.600519&fields1=f1&fields2=f51,f53&klt=101&fqt=1&lmt=3"
  ```
  期望：`HTTP 200`（不通则为 `000`）

**A-3｜限流是双向的，必须写进设计**

【实测】东财硬封 + Yahoo 429，两者都会发生。**四条纪律必须进 PRD 风险章**：

1. **缓存不是优化，是保护**——重复查询绝不重复出网
2. **绝不激进重试**——被 429/断连后要退避，否则加深封禁
3. **被封时的措辞要诚实**——说"数据源暂时拒绝了请求，过会儿再试"，**不要**说"查不到这只股票"（两回事）
4. **开发调试不打真实接口**，用 fixture

**并保留原 PRD §3.1「只做日线」的价值说明**：正常使用 20 次/天，离触发点有 8 倍以上余量。**这是该决定真正的价值，原文没写透。**
