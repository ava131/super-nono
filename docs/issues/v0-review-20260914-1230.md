## 1. A 级问题（必须改）

### 🔴 A1 — `ctx.signal` 未透传给 `safeFetch`：**"停止"按钮会失效**【实测·本机】

**问题**：SDD 全文**没有出现过 `signal`**（实测 `grep -n "signal" SDD-issues-v0.md` → 0 命中）。

**为什么是缺陷**：`egress.js` 专门实现了"合并调用方 signal 与超时 signal"，并在注释里写明**这是修过的 bug**：

> ⚠️ 这一条是修过的 bug：原设计用 `AbortSignal.timeout()` 直接覆盖调用方 signal，
> 导致用户按「停止」时请求不会被中断（要干等到超时），违反 B-2c。

技能如果不把 `ctx.signal` 传进去，就会**把这个已修的 bug 重新引入**——而且是静默的：查询照常出结果，只是"停止"在 15 秒超时前无效。

**改法**：`ctx.safeFetch(url, { signal: ctx.signal, ... })`。并在 SDD §5.2 与测试策略里各加一条。

```js
const res = await ctx.safeFetch(url, {
  headers: { Accept: 'application/vnd.github+json', 'User-Agent': UA },
  signal: ctx.signal,        // ★ 必须传：否则"停止"要等到超时才断
});
```

### 🔴 A2 — SDD 自相矛盾：缓存到底存什么？【实测·本机】

**两处结论相反**：

| 位置 | 原文 | 主张 |
|---|---|---|
| SDD §5.4 | 「存什么 \| **已排版好的行数组** + 元数据」 | 存**排版结果** |
| SDD §6.2 | 标题「缓存条目形状」，内容是 `items: [{repo, number, title, url, …}]` | 存**结构化数据** |

**必须统一为「结构化 items」**，两个理由：

1. **排版规则会改**（标题截断 55、label 取 2 个都是可调参数）。存排版结果的话，改了 `format.js` 之后**旧缓存还在吐旧格式**，且 TTL 内无法察觉。
2. **缓存命中时要能重建 `data`**（PRD §6.3 的"无损通道"）。存排版结果就重建不出来。

**改法**：删掉 §5.4 那一行，统一按 §6.2 的形状；把 §5.4 的"理由"换成上面两条。

### 🔴 A3 — PRD §5.2 漏了 `windowDays` 参数【实测·本机】

**证据**：

```
PRD §5.2 schema 里的参数：  domain / repos / limit
SDD 里出现 windowDays 的次数：3（buildQuery 入参、缓存 key、§3.4）
```

**后果不只是文档不一致**：校验器 `schema.js:211` 对**未声明的字段是"忽略"**（注释：「模型偶尔会多塞一个字段，为这个让它重试一整轮不值得」）。所以模型传 `windowDays` 时会被**静默丢弃**，永远用不上——文档承诺的能力实际不存在。

**改法**：把 `windowDays` 加进 PRD §5.2 的 `properties`：

```jsonc
"windowDays": {
  "type": "integer", "minimum": 1, "maximum": 30,
  "description": "只看最近 N 天内更新过的 issue，默认 7"
}
```

> 注意：PRD §3.1 的配方写的是 `updated:>{today-7d}`，措辞是"默认 7 天"——**说明作者本来就打算让它可调**，只是漏写了 schema。

## 1.5 A4 — `description` 有 200 字硬上限，初稿 372 字**导致技能被禁用**【实测·本机】

**这是实施阶段才暴露的问题，也是本文档最重要的一条。**

`pnpm skill:list` 实测输出：

```
── 被禁用的技能 ──
  ✖ github_issues: github_issues: description 太长了（372 > 200 字），模型看不完
```

`schema.js:74` 的 200 字上限是**硬性**的：超了不是警告，是 `registry.loadSkills()`
把它放进 `failed`，技能**直接不可用**。

**连锁后果：它推翻了 PRD §4.5 的原方案。** 原方案要求"领域清单写进 description，
并用测试断言两份清单一致"——但 200 字要装下「何时使用 + 反问指令 + 只呈现不分析」
已经很紧，**领域一多必然超限**。那个方案不可扩展。

**已改的方案（更简单，也更可靠）**：

```
模型不带参数调用 github_issues({})
  → NEED_DOMAIN 返回领域清单（0 次网络请求）
  → 模型据此反问用户
```

好处：① 清单只有 `known-domains.json` **一个来源**，根本不存在"两张清单漂移"；
② 加领域不用碰 description；③ 反问由代码保证，不依赖模型记得住。

**同时补上了一条本该一开始就有的测试**：用真校验器 `validateManifest()` 跑一遍
`skill.json`。它在 `pnpm test` 里能当场抓住这个问题，而 `pnpm skill:list`
只在角落的小字里报错——**起草时没人会去看那里**。

> 教训：**文档里声称的代码事实，必须在实施阶段用一次真实加载验证。**
> 本文档 §4 核对的是"我引用的函数行为对不对"，但漏掉了"我写的 manifest 能不能过校验"。

## 2. B 级问题（会造成测试不稳或行为不确定）

### 🟠 B1 — `buildQuery` 用了 `Date.now()`，测试会偶发失败

SDD §5.2 的 `buildQuery` 内部调用 `Date.now()` 算窗口日期。后果：

- T1/T10/T15 断言查询串时，**跨零点运行会失败**
- 跨时区 CI 会失败（`toISOString()` 是 UTC，本地日期可能差一天）

**改法**：把 `now` 变成显式参数并默认 `Date.now()`：

```js
export function buildQuery({ repos, windowDays, excludeLabels, now = Date.now() })
```

测试传固定 `now`，断言变为**确定性**的。

### 🟠 B2 — `domain` 与 `repos` 同时给出时，优先级未定义

SDD §5.6 只说"`repos` 跳过领域表"，没写两者同时出现怎么办。

**改法（建议）**：**`repos` 优先，`domain` 被忽略**；并在 description 里写明，避免模型两个都传时行为不可预测。

### 🟠 B3 — 预算裁剪掉条数时没有"如实告知"

SDD §5.5 的裁剪是 `while (… > 800) lines.pop()`——**静默减少条数**。

这正是 market 已经踩过的坑，`snapshot.js` 的注释记着这条教训：

> **列必须固定**：原稿"先去掉量比列、再去掉区间位置列"会让列数变化

market 因此改成"列不许按需删"。本技能的"删整行"比"删列"轻，但**同样是静默降级**。

**改法**：裁剪发生时，summary 必须写出**"共 N 条，这里列了 M 条"**。PRD §2.3 已经允许这个说法（「说明'共查到 N 条，这里列 5 条'」），但 SDD §5.5 没把它变成硬要求。

**过程中新发现并修掉的 5 个问题（起草时都没预料到）**：

1. **`renderLine` 会把 `undefined` 渲染成网址**——`formatSummary` 因此加了
   `hasUsableUrl()` 过滤。整个技能的存在理由就是"网址是模型唯一无法自己生成的事实"，
   渲染出字符串 `undefined` 等于**把坏链接当事实讲出去**。
2. **`query.js` 的注入面**——`repos` 是模型直接给的不可信输入，会被拼进搜索查询串。
   `REPO_RE` 的字符集不含空白与 `:`，从根上堵掉
   `owner/repo updated:>2000-01-01` 这类查询篡改。
3. **`summary` 结尾没有写出查询窗口**（真实运行阶段发现）。
   实测中**模型主动把 `windowDays` 从默认 7 收窄到了 1**，据此说"今天（09-16）有更新的 issue"——
   复现验证后确认它**说得对**（`updated:>09-15` 恰好就是今天，`total=79` 精确吻合）。
   但 footer 当时只有「共 79 条匹配」：**同一句话背后可能是 1 天也可能是 7 天，输出无法自证范围**，
   而模型转述时完全可能把它说成"最近一周"。
   → 已改为窗口**永远出现**：`最近 1 天，共 79 条匹配，这里列了 5 条`。
   原设计只考虑了"裁剪告知"（B3），漏了"范围告知"。
4. **缓存 key 不合法 → 缓存 100% 静默失效**（最严重的一条，且**我两次误报为"已验证"**）。
   `ctx.store` 用 `KEY_PATTERN = /^[A-Za-z0-9_:.-]{1,64}$/` 校验 key，而最初拼的是
   `[domainId, repos.join(','), …].join('|')` —— **仓库名里的 `/`、分隔符 `|`、逗号全都不合法**，
   而且 67 字符还超了 64 上限。
   每一次读写都抛 `BAD_ARGS`，而**缓存失败按设计是被吞掉的**（缓存是优化不是正确性），
   于是**既不报错也不生效**：`skill_kv` 里一条 `github_issues` 记录都没有。
   → key 改为**按构造就合法**：`gh:v1:{domainId}:{windowDays}:{limit}:{sha256(repos|labels)前12位}`，
   定长 33 字符，全部落在允许字符集内。
5. **`scripts/skill-test.js` 从不调用 `initDb`** → `ctx.store` 的 `getDb()` 必然抛错，
   **CLI 里缓存永远不生效**。而 CLI 恰恰是"验证缓存有没有生效"最该能用的地方。
   → 已加 `initDb(':memory:')`（单进程，不落盘、不污染 `nono.db`）。

> **这两条合起来给了一记教训**：我把"缓存失败必须容错"当成了正确性保障，
> 但**容错同时消灭了唯一的失败信号**。所以这类"防弹"设计**必须配一条穿过真实校验器的测试**
> ——现在的 T21 就是：假 store 但每次读写都过一遍**真实**的 `checkKey`，key 一旦不合法当场就炸。
