## 2. A 级：会让代码写错或写不出来

### A1 — 缓存键不合法（**阻断**，且能通过全部既有测试）【实测·本机】

- `store.js:40`：`KEY_PATTERN = /^[A-Za-z0-9_:.-]{1,64}$/`，`checkKey()`（`store.js:69`）不匹配就 **抛 `BAD_ARGS`**。
- SDD §5.4 的键：`` `${domainId}|${repos.join(',')}|${windowDays}|${limit}` ``。
  - `|`、`,` **不在**允许字符集 → 抛错。
  - 用 ai-infra 种子计算长度：`ai-infra|vllm-project/vllm,sgl-project/sglang,vllm-project/vllm-ascend|7|5` = **74 字符 > 64**。
- 两种结局都坏：① 若 `cache.get` 未包 try → **整个查询失败**；② 若包了 try 容错 → 缓存**永远不命中**，每次都真出网，直接触发 R2（10 次/分钟）。
- **为什么测试抓不到**：SDD §8.1 的 L2 用 mock `store.cache`，mock 不跑 `checkKey`；T11/T12 会**通过**。
- **改法**：键改成 `ghissues:{domainId}:{windowDays}:{limit}:{reposDigest8}`，全部字符合法、长度可控（`reposDigest` 用一个自写的 8 位 FNV-1a/base36，纯函数可测，不引依赖）。
- **测试**：T11 必须用**真的** `createSkillStore`（`store.js:212`），不是 mock。`test/unit/store.test.js` 已经证明可以在 `node:test` 下用 `initDb(':memory:')` 建真库，成本为零；再加一条 `assert.doesNotThrow(() => checkKey(key))`。

### A4 — `limit` / `windowDays` 没有默认值兜底【实测·本机】

- PRD §5.2 说 `limit` "默认 5"，但那只是**给模型看的 description**。`schema.js:180` 注释明确列出校验器只支持 7 个关键字，**`default` 不在其中**；`validateArgs`（`schema.js:188-221`）不会补默认值 → 模型不传 `limit` 时，`checked.value.limit` 是 `undefined`。
- SDD §5.2/§5.5 没有一处写"`limit = args.limit ?? 5`"，而 §5.2 的请求拼装是 `per_page={limit}` → **`per_page=undefined`**。

### A5 — `repos` 参数没有形状校验 → 查询注入 + 静默截断【实测·本机】

- 校验器**不支持 `pattern`/`maxItems`**（`schema.js:180`）。SDD §5.1 的 repo 形状校验（`/^[\w.-]+\/[\w.-]+$/`）**只作用于 `known-domains.json`**，**没有作用于模型传入的 `repos`**；SDD §5.2 对 `repos` 只写了"clamp 到 5"。
- 后果：
  1. **查询注入**：`repos: ["foo bar is:pr"]` 会被拼进 `q`，等于让模型（或一个被注入的标题，见 B6）改写查询语义；`repos: ["-label:bug"]` 同理。
  2. **静默丢弃**：用户给了 8 个合法仓库，clamp 到 5 后**不告诉用户**——又一个"看起来很正常的错答案"。
- **改法**：`repos` 逐项过 `/^[A-Za-z0-9._-]+\/[A-Za-z0-9._-]+$/`（GitHub 的 owner/repo 字符集），去重、保序、clamp 到 5；**非法项与超限项都要写进 summary**（"忽略了 2 个不合法/超出上限的仓库名"）。
- **测试**：T10 补断言——非法项被丢弃且出现在 summary、`q` 里不含 `is:`/`-label:` 等注入片段。

### A6 — AS1 的 "vllm" 解析路径不存在【实测·本机】→**【已决 · PM 2026-09-16】**

## 3. B 级：会给出错误答案或错误提示

### B1 — 仓库不存在时说"最近没更新"（假话）【实测·本机】→**【已决 · PM 2026-09-16】**

- GitHub **搜索**对不存在的 `repo:` **不报错**，返回 `total_count: 0`；SDD §5.6 的"无结果"态会对用户说「这 N 个仓库最近 7 天没有更新」。
- 仓库改名/转移后同样如此（`/repos/` 会 301，搜索不会）。这是 PRD R1「静默返回错误答案」在 repos 路径上的**原样复发**，而 R1 被 PRD 自己列为最高优先级风险。
- **PM 裁定**：**用 core 配额逐个 `GET /repos/{owner}/{repo}` 校验存在性，不存在的明确报错。**
- **执行**：
  - 只在**显式 repos 路径**做（领域路径的仓库由本地表保证存在，且验收时已 `/repos/` 核实过）。
  - `core` 配额与 `search` **相互独立**（`x-ratelimit-resource` 可区分），不抢那 10 次/分钟；未认证 core 是 60/小时，最多 5 个仓库 → 一次最多 5 次 core。
  - 结果进 `data`（`repos: [{full, exists}]`）+ summary 如实说明"这些仓库名我找不到，请核对：…"。
  - 失败路径：core 也限流时**不能**把"校验不了"说成"仓库不存在"，要分开措辞（照 `skills/market/prompts.js` 的 `FAILURE_WORDING` 思路）。
- **测试**：T 新增「repos 含不存在仓库 → `ok:false`/明确警告，且**不**说"7 天没有更新"」。

### B2 — GitHub 查询的两条硬限制：256 字符 + **最多 5 个 AND/OR/NOT 操作符**【文档】

- 官方文档（[Troubleshooting search queries](https://docs.github.com/en/search-github/getting-started-with-searching-on-github/troubleshooting-search-queries)）明文两条：**"不支持长度超过 256 个字符的查询"**、**"无法使用超过五个 AND、OR 或 NOT 运算符构造查询"**。
- SDD §5.2/§10-S7 把 256 标成"**未验证**"——其实它是**官方明文**，可以直接升级为【文档】；（256 与我们的最坏情况相比是宽松的：5 个 repo ≈ 125 字符 + 过滤条件 ≈ 60。）
- **真正危险的是操作符上限，两份文档都没提**：`A1 .. A5` 里 `repo:a repo:b repo:c` 是隐式 OR，`-label:x` 是 NOT。3 repo + 1 label 已经 3–4 个；**5 个 repo + 2 个 `excludeLabels` = 5 个 OR + 2 个 NOT，正贴/越过上限**，而 SDD §5.2 允许 `repos` 到 5、§7.7 又鼓励按领域声明多个 `excludeLabels`。
- 【未验证】重复限定符是否按操作符计数（各来源说法不一）。**必须在步骤 6 顺手实测一次**：`is:issue state:open repo:a repo:b repo:c repo:d repo:e updated:>DATE -label:x -label:y` → 看 200 还是 422。
- **改法（保险起见）**：① 把 `excludeLabels` 也 clamp（如 ≤2），与 `repos` 一起算总操作符预算并在代码里断言；② 优先用 §6-P1 的 `org:`/`user:` 折叠（直接省操作符）；③ 触发 422 时按 SDD §5.3 返回 `INTERNAL` 并带上查询串——这条现有设计是对的。

### B3 — `NEED_DOMAIN` 的领域清单会被 800 静默截断【实测·本机】

- `NEED_DOMAIN` 的 summary 走 `runner.js:196-202`，最终 `String(...).slice(0, SUMMARY_LIMIT)`（`runner.js:200`）——**静默截断**，正是 PRD §6.1 自己画红线的那个行为。
- 领域表只有 1 条时看不出问题（这也是 v0 只发 1 个领域的另一个好处），但它是一条**随数据增长必然爆发**的隐患。
- **改法**：`NEED_DOMAIN` 自己排版并**自己保证 ≤800**：每行 `- {id}：{label}`，超出预算时截到 N 条 + 明确写「（还有 M 个领域，你说个方向我再查）」。→ 与 §5.5 的"技能自己保证 ≤800"是同一条纪律，写进 SDD。

### B4 — 403 被简化为一种语义【实测·本机】

- SDD §5.3 只处理"403/429 → 读 `x-ratelimit-reset` → 说『约 N 秒后恢复』"。GitHub 的 403 至少三种：① 主限流（`x-ratelimit-remaining: 0`、`x-ratelimit-reset` 有效）；② **次级限流**（并发/短时突发，带 `retry-after`，`remaining` 可能不为 0）；③ **abuse/风控**（可能没有可信的 reset）。
- 对 ②③ 说"约 N 秒后恢复"是**编造一个数字**——违反 PRD §2 的精神。
- **改法**：`remaining === 0 && reset > now` → 报秒数；否则 → 中性措辞「GitHub 暂时拒绝了请求，过一会儿再试」，并读 `retry-after`（有就用，没有就不编）。照 `market/prompts.js` 的 `FAILURE_WORDING` 写成**机器可判定**的措辞规则 + 测试。

### B6 — issue 标题是**外部不可信文本**，风险表零覆盖【实测·本机】

**1. 外链必须走"主进程校验 + `shell.openExternal`"，不能直接 `<a href>`**

全仓库目前**没有** `will-navigate`、也**没有** `setWindowOpenHandler`（`main.js:65` 只有 `shell.openPath`）。气泡窗是一个 `BrowserWindow`，直接放 `<a href="https://github.com/…">` 点击后会**把整个应用界面导航走**（用户看到应用"变成"了 GitHub 网页，回不来）。
要求：新增"打开外链"IPC 通道 → 主进程校验 `protocol === 'https:'` **且** `hostname === 'github.com'` → 才 `shell.openExternal`；同时给气泡窗装 `will-navigate` 拒绝一切站内导航。

**2. 渲染端注入（B6 的另一半）**

issue 标题是外部不可信文本，现在要**进 DOM**。必须 `createElement` + `textContent`，并加一条断言"渲染路径里不出现 `innerHTML`"。B6 的测试从"summary 是单行"扩展到"渲染函数不产出 HTML"。

**3. `limit` 的语义分裂 → 建议直接定死（这条同时把 P2 从可选变成必须）**

- `limit`（1–5）：只控制**模型可见的叙述条数**；
- `per_page`：固定成一个展示常量 `DISPLAY_COUNT`（**建议 10**，上限 20）——同一次请求，配额不变。

由此 **§6 的 P2 变成硬要求**：缓存必须存 **`items`**（而不是 SDD §5.4 写的"只存已排版好的 5 条"），summary 在**读取时**按 `limit` 现排；**缓存键里不能再有 `limit`**（否则同一个领域因为叙述条数不同而重复出网）。体积核对：20 条约 8KB，远低于 `MAX_VALUE_BYTES`（64KB，`store.js:43`）。

**4. AS6 要重述**：原文「返回 6 条**不会发生**」现在只对**模型可见的 summary** 成立；气泡可以展示 6–20 条。PRD §6.1 的 800 预算仍是硬约束，但作用域要写清楚（**约束 summary，不约束气泡**）。

- AS17：标题里含 HTML/脚本（如 `<img onerror=…>`）时，气泡只把它当**纯文本**渲染。
