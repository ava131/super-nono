## 1. 背景与目标

### 1.1 一句话描述
Skill 是桌宠"能做的事"。每个技能是一个**自包含目录**，里面声明"我是什么、需要什么参数、有什么权限、要不要用户确认"。Brain 把这些声明转成模型的工具清单，模型决定何时调用。

**v0 的关键目的不是"功能多"，而是验证框架**：技能注册 → 转成工具清单 → 模型决策 → 参数校验 → 执行 → 结果回填 → 模型叙述，这条链路必须完整跑通。天气技能是这条链路的**验证样本**。

### 1.2 v0 目标

| 编号 | 目标 | 可衡量标准 |
|---|---|---|
| G1 | 有统一契约 | 新技能只需加一个目录 + 一份声明文件，不改 Brain 代码 |
| G2 | 有权限闸门 | 每个技能必须声明权限，越权调用直接被拒 |
| G3 | 有确认机制 | 机制就位（v0 唯一的技能是只读的，不触发确认） |
| G4 | 白名单出网 | 除声明的域名外，任何技能都发不出请求 |
| G5 | 天气可用 | 问"上海天气怎么样"能给出真实、可核对的数据 |

### 1.3 v0 非目标（移交 v1+）

- ❌ 股价查询与分析
- ❌ 邮箱归类 / 摘要 / 草拟 / 发送
- ❌ 提醒 / 定时任务
- ❌ 长期记忆读写
- ❌ 网页搜索
- ❌ 文件整理、截屏
- ❌ 技能商店 / 在线安装 / 第三方分发
- ❌ 图形化技能编辑器

## 3. 技能契约【v0 · 冻结】

> 这是本项目的架构骨架。v0 只实现一个技能，但契约必须一次定对，否则后面每加一个技能都要改 Brain。

### 3.1 目录结构

```
skills/
  weather/
    skill.json        ← 声明（给 Brain 和模型看）
    index.js          ← 执行器（默认导出 run 函数）
    README.md         ← 可选
```

### 3.2 声明文件 `skill.json` 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 唯一标识，小写下划线 |
| `description` | ✅ | **给模型看的**，"什么时候该用它"。写得好坏直接决定调用准确率 |
| `parameters` | ✅ | JSON Schema 对象，描述入参 |
| `permissions` | ✅ | 权限数组，见 §4.1 |
| `risk` | ✅ | `read_only` / `local_write` / `external_send` / `irreversible` |
| `requiresConfirmation` | ✅ | 布尔。`risk` 非 `read_only` 时**强制为 true** |
| `timeoutMs` | ✅ | 单次执行超时，默认 15000 |
| `networkHosts` | 条件 | 需要出网时必须列出域名白名单，否则出网被拒 |
| `version` | ✅ | 技能版本 |

### 3.3 执行器契约

- 默认导出 `run(args, ctx)`，返回结构化结果。
- 参数必须**先经 zod 校验**，不合格直接返回错误（**不执行任何副作用**）。
- 返回值约定：
  - 成功：`{ ok: true, summary: "给模型看的简短文本", data?: {...} }`
  - 失败：`{ ok: false, code: "TIMEOUT|NOT_FOUND|AUTH|RATE_LIMIT|EGRESS_DENIED|INTERNAL", message: "..." }`
- **`summary` 是给模型读的，必须简短**（≤ 800 字符）。原始大块数据走 `data`，由 Brain 决定是否落盘，**不进上下文**。
- 执行器不得自己弹窗、不得直接操作界面；需要确认时通过 `ctx.requestConfirmation()` 发起。
- 执行器不得吞掉错误，统一由 Brain 的错误处理接管。

### 3.4 新增一个技能的标准步骤

1. 建目录 `skills/<name>/`。
2. 写 `skill.json`：定 `description`、`parameters`、`permissions`、`risk`、`networkHosts`。
3. 写 `index.js` 导出 `run`，用 zod 校验入参。
4. 本地自测：`pnpm skill:test <name> '<json参数>'`（**不经模型**，单技能直调）。
5. 重启应用，模型自动看到新技能（注册表启动时扫描目录）。

## 4. 权限与确认机制【v0 建机制，v1+ 才用得上】

### 4.1 权限清单

> **C-5 修订：取消"默认允许"的概念。**
> 原稿 §3.2 把 `permissions` 定为**必填**，但 §4.1 却把 `db:cache` / `db:memory` / `notify` 标成"默认允许"——结果是 weather **不写 `db:cache` 也能用缓存**，必填字段的实际约束力为 0，声明与生效不一致。
> **现定死：所有权限一律显式声明，未声明即为拒绝。** 没有默认放行项。

| 权限 | 含义 | 未声明时 |
|---|---|---|
| `network:<tag>` | 允许出网，域名必须在 `networkHosts` 内 | **拒绝** |
| `fs:read:<path>` | 允许读取指定路径（需用户显式授权的目录） | **拒绝** |
| `fs:write:<path>` | 允许写入指定路径 | **拒绝** |
| `db:cache` | 允许读写本地持久化缓存表（**v0 无人使用**，v1+ 行情技能会用） | **拒绝** |
| `db:memory` | 允许读写长期记忆（v1+） | **拒绝** |
| `notify` | 允许弹气泡 / 托盘提醒 | **拒绝** |
| `credential:<name>` | 允许读取钥匙串中的某项凭据 | **拒绝** |

- **权限在代码层强制，不靠模型自觉**：技能发起网络请求时走统一出口函数，域名不在白名单 → 直接抛错 + 记日志。
- **v0 的 weather 只声明一个权限：`network:weather`。** 它的 10 分钟缓存走**进程内内存**，不涉及 `db:cache`（见 §6.3）。

### 4.2 三级风险模型（human-in-the-loop）

| 级别 | 判定 | 行为 | v0 实例 |
|---|---|---|---|
| **L1 自动执行** | 只读、纯本地、无隐私 | 直接执行，事后气泡告知 | `weather` ✅ |
| **L2 需确认** | 外发数据、写本地文件、读隐私内容 | 宠物弹气泡显示**完整将要做的事**，点确认才执行 | 无 |
| **L3 禁止** | 涉及金钱或不可逆后果 | **代码层硬拒绝**，模型说什么都不执行 | 无 |

- 确认气泡必须显示：调用哪个技能、用什么参数、会发送什么内容、去向哪里。**不允许"盲确认"。**
- **L2 确认的"本次会话内记住"——v0 不做**（评审建议 3）。它是个安全相关的记忆，v1 的 email 技能才用得上；现在做等于增加一条没人测的攻击面。v0 干脆全不记住。

### 4.3 网络白名单（"不外流"的执行手段）

- 全局维护一份域名白名单，来源是各技能 `networkHosts` 的并集。
- 所有出网请求统一走 `safeFetch(url, opts)`：
  1. 解析域名 → 不在白名单 → 抛 `EGRESS_DENIED` 并记日志。
  2. 强制 HTTPS。
  3. 记录请求域名、耗时、状态码（**不记录完整响应体**）。
- 飞行模式开启时，`safeFetch` 直接拒绝一切请求。
- 白名单在设置面板可见，让你随时知道"这个桌宠会跟谁说话"。

## 5. 与 MCP 的关系

- **接口形状向 MCP（Model Context Protocol）的 tool 定义靠拢**：名称 + 描述 + JSON Schema 参数 + 结构化结果。将来接 MCP 生态几乎不用改上层。
- **v0 不引入 MCP SDK**：自用的一个技能，自己写薄注册表更小更可控（符合资源优先原则）。
- **v1+ 再评估接入 MCP 客户端**：好处是现成 MCP server（文件、浏览器、日历）零成本变成技能；代价是多一个依赖与进程管理负担。
- 决策：**先自研薄注册表，接口保持 MCP 兼容形状**——这是一条可逆路径。

## 6. v0 技能详述：`weather`

### 6.1 能力

| action | 说明 |
|---|---|
| `now` | 指定城市当前天气：温度、体感、湿度、天气现象、风速 |
| `forecast` | 指定城市未来 1–3 天：最高/最低温、天气现象 |

- 支持入参：`{ city: string, action: "now" | "forecast" }`。
- 城市名支持中文（如"上海"）与英文（如"Shanghai"）。

### 6.2 数据源选型（关键：**不需要 API Key**）

| 优先级 | 服务 | 接口 | 说明 |
|---|---|---|---|
| 主 | **Open-Meteo** | 地理编码 `geocoding-api.open-meteo.com/v1/search`；天气 `api.open-meteo.com/v1/forecast` | 免费、**无需注册与 Key**、返回 JSON、字段规范、社区活跃 |
| 备 | **wttr.in** | `wttr.in/<city>?format=j1` | 免费无 Key，用作主源失败时的降级 |

**为什么这样选**

- **零 API Key** → v0 的密钥管理面只有 DeepSeek 一个，直接呼应 `PRD-Brain-v0.md` §2.1 P-2 的红线。
- **不引入 Python 生态的天气库** → 保持"单一 Node 运行时 + 零额外进程"的架构。
- Open-Meteo 的天气接口需要经纬度，因此流程是**两步**：先地理编码拿经纬度，再查天气。两步结果都缓存。

### 6.3 执行流程

1. 校验入参（zod）。
2. 查**进程内内存缓存**（主进程内的 `Map` + TTL，同一城市 **10 分钟内不重复请求**）→ 命中则直接返回。
   - **v0 缓存不落 SQLite**（C-3 修订）：数据量极小、零 IO、零 schema 变更，重启后失效对体验无影响。因此 weather **不需要 `db:cache` 权限**。
3. 未命中：`safeFetch` 调地理编码 → 拿到 `latitude` / `longitude` / 规范化地名。
4. `safeFetch` 调天气接口 → 拿当前与预报数据。
5. 本地把 **WMO `weather_code` 映射为中文天气描述**（本地映射表，不依赖模型翻译）。
6. 组装 `summary`（≤ 800 字符，含城市名、温度、天气、体感、湿度、以及**数据时间戳**）。
7. 原始 JSON 放 `data`，由 Brain 决定是否缓存。

### 6.4 硬性规则

| 编号 | 规则 |
|---|---|
| WX-1 | 同一城市 **10 分钟内不重复请求**；全局限流 ≤ 1 请求/秒 |
| WX-2 | 所有数值（温度、湿度、风速）必须来自接口，**模型不得自行编造或"估算"** |
| WX-3 | `summary` 必须带**数据观测时间**，避免把过期数据当实时 |
| WX-4 | 城市无法识别（地理编码无结果）时，明确返回 `NOT_FOUND` 并列出候选城市，**不许猜** |
| WX-5 | 主源失败自动降级到备源；两源都失败则返回 `INTERNAL`，让模型如实说"查不到" |
| WX-6 | 出网域名仅 `geocoding-api.open-meteo.com`、`api.open-meteo.com`、`wttr.in` 三个 |

### 6.5 声明文件示例

```json
{
  "name": "weather",
  "description": "查询指定城市的实时天气与未来几天预报。当用户问某地天气、温度、下不下雨、要不要带伞时使用。",
  "version": "0.1.0",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名，如 上海 / 北京 / Tokyo" },
      "action": { "type": "string", "enum": ["now", "forecast"], "description": "查当前天气还是未来预报" }
    },
    "required": ["city", "action"]
  },
  "permissions": ["network:weather"],
  "networkHosts": ["geocoding-api.open-meteo.com", "api.open-meteo.com", "wttr.in"],
  "risk": "read_only",
  "requiresConfirmation": false,
  "timeoutMs": 10000
}
```

### 6.6 已知待实测项

- **中文城市名的地理编码识别率**：Open-Meteo 的 geocoding 对中文支持需实测；若识别率差，**兜底方案是内置一张常用城市经纬度表**（约 50–100 个主要城市）作为前置匹配。
- 两个源返回的天气现象编码体系不同（WMO code vs wttr.in 自有 code），需各写一份映射表。

## 9. 验收标准

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AS1 | 可扩展 | 新增一个技能只加目录，不改 Brain 代码 |
| AS2 | 描述生效 | 问"上海天气怎么样"能自动路由到 `weather` |
| AS3 | 参数校验 | 传入畸形参数时返回明确错误，不执行 |
| AS4 | 越权拒绝 | 未声明权限的请求被硬拒绝并记日志 |
| AS5 | 出网白名单 | 请求白名单外域名失败（用临时测试代码验证） |
| AS6 | 飞行模式 | 开启后技能出网被拒 |
| AS7 | 确认闸门 | 构造 L2 场景，未确认时**绝不执行** |
| AS8 | L3 红线 | 尝试触发下单/付款类操作，代码层直接拒绝（用桩验证） |
| AS9 | 数据真实 | 天气数字与公开数据源人工核对一致 |
| AS10 | 时间戳 | 回复中带有数据观测时间 |
| AS11 | 城市未识别 | 输入不存在的城市，明确报"找不到"，不编造 |
| AS12 | 降级 | 手动屏蔽主源，能自动切到备源 |
| AS13 | 超时 | 技能卡住时 **10s 内**被强制中断，对话不卡死。⚠️ 这与 `PRD-Brain-v0.md` AB2（**用户主动取消 <1s**）是**两个不同场景**，测试用例不要混 |
| AS14 | 缓存限流 | 10 分钟内重复查询同一城市，不产生第二次网络请求 |
| AS15 | 零依赖 | `package.json` 的运行时依赖中除 Electron 生态外为空 |

## 10. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 公开天气接口变更 / 限流 | 技能失效 | 主备双源 + 可插拔适配器；失败就明说"查不到" |
| 中文城市地理编码识别不准 | 查询失败或查错城市 | 内置常用城市经纬度表兜底；多结果时返回候选让用户选 |
| 模型编造天气数字 | 误导 | 数字必须来自技能；技能不可用时禁止模型自行回答 |
| 技能越权访问文件 | 数据风险 | 权限在代码层强制 + 路径白名单 |
| 依赖膨胀 | 违背资源优先 | v0 保持零运行时依赖（AS15 验收） |
| 模型乱调技能烧 token | 成本上升 | 单技能连续失败 2 次禁用；工具结果截断；每日上限 |
